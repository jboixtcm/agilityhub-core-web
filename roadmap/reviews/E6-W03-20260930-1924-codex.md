# Review E6-W03 — needs changes

## Findings

1. **major** `apps/clubs-admin/src/followup/unread.tsx:113` — Failed reads do not reliably undo the optimistic counter decrement. The catch only refetches the count; when connectivity is lost, that request also fails and leaves the decremented value. An in-memory React reproduction produced **5 → 4 after failure → 3 after another failed retry**, without any successful read. This leaves round-2 item 1 incomplete (R-10-13). Track and roll back each pending decrement locally, then reconcile with the API. Add a regression test where both the POST and count refresh fail.

2. **minor** `apps/clubs-admin/src/followup/unread.tsx:123` — A successful retry does not update D14’s row state. Reproduced: a read fails, navigate back from D13 to D14, then retry successfully. The server marks the item read and the counter drops, but the row remains highlighted because retry neither updates `FollowUpPage`’s `readIds` nor refetches its list. This violates R-10-13’s consistent read marks. Notify the mounted list of successful reads/retries or invalidate its query; extend the retry test to assert the row’s highlight, not only the counter and dismissed notice.
