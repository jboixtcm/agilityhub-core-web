# Review E5-W05 — needs changes

## Findings
1. **blocker** `apps/clubs-admin/src/training/TrainingRegisterPage.tsx:666-707`: the blocks tab (`?vista=bloquejos`) never stops calling `GET /ring-blocks/filter-values`.
   - **Why:** `loadFilterValues` depends on `rings` (`:706`). `useClubRings` → `useRingCatalog` returns a new `{ ...state, refetch }` object on every render (`packages/api-client/src/ring-blocks.ts:233`), so the callback changes identity on every render.
   - This commit adds `setLearned((current) => ({ ...current, … }))` (`:698`), which always creates a new object and so always re-renders.
   - `UniversalList` re-runs its values effect whenever `loadFilterValues` changes (`packages/ui/src/universal-list.tsx:366-390`). It then fetches again and calls `setLearned` again, and so on.
   - The loop starts on mount: `filterField` starts at the first filter column, `ringId`. Only `from` returns before `setLearned`.
   - Each round also calls `setFilterValue(values[0])`, so a ring the user picks snaps back to the first option. The ring filter is unusable, and the tab keeps hitting the api for as long as it is open.
   - The bookings tab (`:387`) has stable deps and is not affected. Before this commit, the blocks deps already held `rings`, but nothing set state, so there was no loop.
   - **Fix:**
     - Remove `rings` from the deps (read it through a ref, or memoize what `useRingCatalog` returns).
     - Make `setLearned` return `current` when no label changed.
     - Add a test: mount the blocks tab, let it settle, and assert exactly one `filter-values` request. Then pick the second ring and assert it stays selected.
2. **major** `TrainingRegisterPage.tsx:678-694` (assumption A2): the blocks' day filter is neither complete nor the api's.
   - **Why:** `/ring-blocks/filter-values` returns "the top 50 values of field", and filters on `from` itself are left out. Each `from` value is a single start instant, so almost every count is 1.
   - The front groups those 50 arbitrary instants into days (the mock returns the 50 oldest). Current days can be missing and day counts come out too low. That is exactly what step 5 forbids ("complete filter values", "never the rows of one page").
   - The front also derives each block's club-local day from the instant (`clubToday(tz, instant)`), which goes against the fixed convention "the front computes no date that the api owns".
   - `/ring-blocks` publishes no day-level filterable field (`x-filterable: id, ringId, kind, reason, state, from, to`). No test covers the grouping. The labels («dl 3») also omit the month although the values span all time.
   - **Fix:** ask @organizer/api for a filterable `date` on `/ring-blocks` (as `/training-bookings` has). Until then, offer no suggested values for `from` (a plain date input with `between`), and record it as an assumption.

7. **minor** `apps/clubs-admin/src/catalogs/JobsCard.tsx:457-460`: the `Week` effect link computes `mondayOf(addDays(key, 1))`.

8. **minor** `scripts/e2e-core.sh:65-73` (step 20): the INT trap may never fire on Ctrl-C in an interactive terminal (reasoned, not run).
   - **Why:** `docker compose run` without `-T` gets a TTY there and puts the terminal in raw mode, so Ctrl-C goes to the container as a keystroke. Playwright then exits 130, `|| status=$?` swallows it, and the script starts the next stage anyway.
   - **Fix:** after each stage, `(( rc == 130 || rc == 143 )) && exit "$rc"`, or pass `-T`.
   - The evidence also does not prove `--profile e2e`: `run --rm` removes the one-off container on every normal exit, so logs `51`/`56`/`70` would be empty without the change. `70` holds only `exit 0`, without the command.
