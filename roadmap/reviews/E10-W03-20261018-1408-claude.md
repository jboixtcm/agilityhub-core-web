# Review E10-W03: needs changes

## Findings
1. **major** `e2e/core/e10-core.spec.ts:341`: the real-core "primary choice" check passes without proving anything.
   - **What's wrong:** `row.getByText("principal")` is Playwright's default match, which is case-insensitive and matches substrings. A VERIFIED domain that is *not* primary renders a [Fes-lo principal] button (`DomainsTab.tsx:300-310`), and that button's text satisfies the locator.
   - **Evidence contradicts the report:** the committed real-core screenshot `roadmap/evidence/E10-W03/core-D19-dominis-verifica-1280.png` shows `minim.example.test` holding the «principal» badge. The newly verified `e10w03-62124.example.test` has only [Fes-lo principal] and [Elimina]. So the comment at :339 and the round-2 report's claim ("the reloaded row's `principal` mark") are false.
   - **Rule:** round-2 point 2 of the organizer's ruling E133 ("asserts … the primary choice") is not met. The rest of that point is genuinely proven: 200, VERIFIED, CNAME, `/internal/domains/allowed` → 200, and the separate 422.
   - **Fix, part 1:** use `{ exact: true }` or target the badge, and also assert that [Fes-lo principal] is absent.
   - **Fix, part 2 (make the choice real), either:**
     - add the domain for an app the «club mínim» has no verified domain for yet (e.g. `clubs-admin`, if the seed has none), so "first verified becomes primary" is real; or
     - click [Fes-lo principal], require `PUT …/primary` → 200, and check the badge moves to the new row.

2. **major** `apps/clubs-admin/src/support/SupportPages.tsx:51-68` + `packages/auth/src/auth-client.ts:780`: reloading `/suport?sortit=1` shows «Has sortit… Ja pots tancar aquesta pestanya» without revoking anything.
   - **Why the token isn't there yet:**
     - The `AuthClient` constructor does not read the stored impersonation.
     - React runs child effects before parent effects, so `SupportEntryPage`'s "leaving" effect runs before `SessionProvider`'s effect calls `restoreSession()`. Only `restoreSession()` → `enterImpersonation` puts the token back into memory.
   - **What happens:**
     - `revokeImpersonation()` sees `accessToken === null && impersonation === null`, returns a resolved no-op, and the page switches to "left". Under StrictMode the cached `revokeAttempt` ref replays that same no-op.
     - Then `SessionProvider` restores the still-live support session from session storage.
   - **How users hit it:** reloading on the "leaving" page (slow network) or on the "leaveFailed" page, where a reload is the natural way to retry, or a browser tab restore.
   - **Rule:** this reintroduces round-2 point 1 / R-17-10 ("a support grant can stay valid while the screen says it has ended"; "pending state until the revocation succeeds").
   - **Fix:** when no in-memory token is held, `revokeImpersonation()` should take the stored `active` token from tab storage, or the page should first wait for `restoreSession()`. A 401 on `/me` there means the access already ended; a network error must lead to "leaveFailed", not "left".
   - **Test:** a fresh `AuthClient` with an active stored token, rendered at `/suport?sortit=1` under StrictMode, must send exactly one revoke with that bearer. Add a variant where the revoke fails, which must show the alert.

3. **minor** `e2e/core/e10-core.spec.ts:471-482`: the real-core «Surt» step only asserts that the revoke answered 2xx and that the copy appears.
   - **What's missing:** proof that the grant is actually dead. R-17-10 (E10-T04 detail) says the token answers 401 after `POST /oauth2/revoke`, and "really ends the access" was the whole point of round-2 item 1.
   - **Fix:** capture the support bearer (from the `/me` request or `revokeResponse.request().headers().authorization`), then call `GET /api/v1/me` with it and expect 401.

4. **minor** `apps/clubs-admin/src/audit/SupportAccessesCard.tsx:109-118`: with paging, a failure on any page (e.g. STARTED page 1) is swallowed (`() => undefined`).
   - **Effect on first read:** the card never appears, so the club's ADMIN silently loses sight of every live grant.
   - **Effect after [Acaba l'accés]:** a failed reread leaves the stale list, including the grant that was just ended.
   - **Why the code comment is wrong:** the comment says "the audit list below says its own read failure". That list is a different query and can succeed while this one fails, so it does not cover the gap.
   - **Fix:** show a `LoadError` with a retry inside the card on failure, and clear or flag the stale list.
   - **Same file, line 66 (offset paging):** paging by offset with `sort at,desc` can return the same STARTED entry on two pages when a new access starts between the reads. That gives duplicate `key={access.id}` items and two [Acaba l'accés] buttons. Dedupe by `entityId`.

5. **nit** `SupportAccessesCard.tsx:63-83`: every opening of «Auditoria» now walks the club's entire STARTED/ENDED history, so the cost grows forever.
   - A grant lives at most `platform.supportAccessMinutes`, so older STARTED entries can never be live.
   - If the audit filter grammar allows `at:gte:`, bound both queries to "now minus the longest grant lifetime". Otherwise, note the growth as a known cost in the report.

6. **nit** `e2e/core/e10-core.spec.ts:285`: the test title cites T-17-03, but it does not assert T-17-03's "`/branding` abans/després".
   - Either drop the id from the title, or add `GET /branding` with that host: `404 UNKNOWN_HOST` before verification, 200 after.
