# Review E9-W03 — needs changes

## Findings
1. **major** `apps/clubs-admin/src/courses/PlacementEditorPage.tsx:205-218` + `packages/api-client/src/core-api-store.ts:121-155`: re-saving an existing placement wipes data. `PUT /placements/{id}` replaces the whole placement (snapshot: "Replaces the placement"). `placementBody` turns every field the editor leaves out into `null`: `displayName`, `scheduledAt`, `grades`, `sizes`, and `mode` when there is no activity. It also always sends `status: "READY_TO_BUILD"`, and the editor sends `thresholdMeters: null`. So the R-16-06 "revisa la col·locació" save, or any small fix, erases the schedule and grades D7 or the calendar stored, resets a custom `warningThresholdM`, can un-archive an ARCHIVED placement, and drops FREE_FLOATING/EVENT mode. **Why:** R-16-05/06 say PUT recalculates the transform and resolved obstacles, nothing more. **Fix:** build the PUT body from the stored placement plus the user's edits; send `status`/`mode` only when the user changes them. Make the "R-16-06" test (`courses.test.tsx:328`) check that those fields survive. Today it only checks versions and `stale:false`, which the mock sets on any PUT.
2. **major** `PlacementEditorPage.tsx:209, 249-259`: the user gets stuck after the course changes. `courseVersion` is the course version read when the page loaded. If someone edits the course meanwhile, the save answers `STALE_VERSION`. The editor assumes the placement changed, re-reads only the placement and shows «Algú ha desat aquesta col·locació…». Every retry sends the same old course version and fails until the page is reloaded. **Fix:** on `STALE_VERSION`, also re-read the course (version and model; `SET_COURSE`), and test it.
3. **major** `CourseDetailPage.tsx:481-489, 667-675`, `PlacementEditorPage.tsx:492-500`: «Registra-ho com a muntat» is offered to an INSTRUCTOR even when `courses.allowInstructorPublish = false`. R-16-07 says the api answers 403 then (the mock enforces it at `course-handlers.ts:1023`), so the button is a dead action. **Why:** AGENTS rule 3, no dead actions. **Fix:** read the parameter the way `activities/shared.tsx:105` does, hide the action, and add a test. The report does not mention this.
4. **major** `apps/clubs-admin/src/planning/PlannedCourseSelect.test.tsx:139-141`: the test can never fail. `expect(field?.querySelector("[role='alert']")?.textContent).not.toBe("")` passes when there is no alert at all (`undefined !== ""`). So "R-16-13 D3: PLACEMENT_RING_MISMATCH is said under the selector" is not checked. **Why:** AGENTS rule 5, tests must really assert the rule they are named after. **Fix:** `expect(within(field).getByRole("alert")).toHaveTextContent(<errors:PLACEMENT_RING_MISMATCH text>)`.
5. **minor** `apps/clubs-admin/src/App.test.tsx:262-268` ("R-16-15 … never the editor"): the test waits only for the «Pistes» link, then checks that no «Geometria…» heading exists. The geometry page is lazy-loaded and fetches its data first, so the test would also pass with COURSES on. **Fix:** assert something the page does show (not-found or module refusal), or add a control case with COURSES on.
6. **minor** `CreateClassDrawer.tsx:52-53, 432`, `SelectedClassCard.tsx:335-337`: `PLACEMENT_RING_MISMATCH` lands under the ring chips (drawer) or in the general alert (card); only `ClassForm` puts it under «Recorregut previst». **Why:** S16 §2 / R-16-13, which the report itself describes as "under the field". **Fix:** add a `placementId` error key in both places. There are no tests for the drawer or the card: POST carrying `placementId`, the reset on ring change, the card without COURSES.
7. **minor** `RegisterSetupModal.tsx:252-268`, `CourseDetailPage.tsx:470-480`: on a stale placement the build sheet mixes the stored `resolvedObstacles`, computed on the old geometry, with the ring's current geometry (markers, doors). The PDF's marker distances can be wrong, and nothing warns the user. **Fix:** disable or warn while `placement.stale` and point to «Revisa».
8. **minor** `RegisterSetupModal.tsx`:
   - `:218-220`: REGISTRA is enabled before the active setup has loaded, so a setup can be replaced without the user ever seeing «Substituirà el muntatge actual…».
   - `:253`: `throw new Error("RING_WITHOUT_GEOMETRY")` is not an `ApiError`, so the user gets the generic message instead of `errors:RING_WITHOUT_GEOMETRY`.
   - `:110-117`: the course's `agilityhubLevel`/`levelIds` are never sent, so students see no level (R-16-09 example «Agility · nivell D»).
9. **minor** `PlacementEditorPage.tsx:229-262`:
   - After `PLACEMENT_BLOCKED`, the failure state stays when the course is moved again, so «Desa igualment» forces a position the api never judged. Clear `failure` on every move or turn.
   - `details.warnings` is stored but never displayed.
   - `:235-237`: if the follow-up GET throws after a successful POST, the user sees an error although the placement was saved, and `?colocacio=` is never set. That re-read should be best effort.
10. **minor** `packages/api-client/src/core-api-store.ts:620-622`: `deactivateMarker` calls `updateMarker` without `geometryVersion`. `#putGeometry` then falls back to the version it just read, which brings back the silent overwrite that the E9-W02 review #2 note asked to remove. **Fix:** require the version the user read.
11. **minor** `RingGeometryPage.tsx`:
   - `:135-153`: the six default markers are always laid out for 40 × 20 m. A new 22 × 30 ring saves markers outside the perimeter and fails `GEOMETRY_INVALID`. Recompute positions from the typed size while the markers are untouched.
   - `:382-383`: the `GEOMETRY_INVALID` details are cast to a hand-written type instead of `components["schemas"]["GeometryViolation"]` (AGENTS rule 4).
   - `:352`: unknown violation paths (e.g. `orientationDeg`) are shown raw to the user.
   - `:679-681`: «Substituït» compares timestamps as exact strings. Compare `Date.parse` values instead.
   - There is no client-side pre-check of [10, 60] or of ≥ 3 non-collinear markers. A non-numeric input is sent as `null` and gets a generic error.
12. **minor** `packages/api-client/src/mocks/course-handlers.ts`: club isolation (R-16-16) is incomplete. These routes never check the caller's club:
   - `DELETE /rings/:id/geometry` (`:938-957`)
   - `PUT /obstacle-inventories/:scope` (`:971-989`), which accepts any `ring:<id>`
   - `GET …/club` (`:961-969`)
   - `dismantle`/`renewal` (`:1106-1143`), which are also not `keyed()` although the snapshot declares `Idempotency-Key`
   - upload keys (`:580`), which always use the fixture club's prefix

   No T-16-05 cross-club test exists. MEMBER reads of `GET /courses/{id}` and `GET /ring-setups/{id}` answer 403 (`:686-691`, `:1012-1019`), contrary to R-16-09/16. This is harmless here, but E9-W04/05 will build on these mocks.
13. **minor** `packages/course-ui/src/lib/pdf/marker-sheet.ts:67`: a marker larger than 190 mm is printed smaller than its stored `physical_width_m`. The size line states the printed size, but the AR app still uses the stored size, so pose and scale come out wrong. **Fix:** refuse the sheet or warn in D16, or store the printed size. Separately, with no active marker the PDF has `/Count 0`, which most viewers reject; the D16 button (`RingGeometryPage.tsx:902`) is not disabled for that case.
14. **minor** `pdf-document.ts:146-153, 353`:
   - Text is not `normalize("NFC")`'d, so decomposed accents and `ŀ` (U+0140) print as «?» in user-typed course, ring and door names.
   - `/Title` is written in WinAnsi but read as PDFDocEncoding (’ → ™).
   - **Fix:** NFC plus an NFKD fallback before «?», and a UTF-16BE title.
15. **minor** `CoursesPage.tsx:70-78, 483-499`: S16 §2 asks for «dates» and the D18 list has no date column. `CourseListItem` has no `updatedAt`, so this is a contract gap the report should raise for the api. The tag and level filters of the universal list are also missing.
