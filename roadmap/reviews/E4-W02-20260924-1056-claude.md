# Review E4-W02 — minor issues

## Findings
1. **major** `apps/clubs-admin/src/planning/CalendarPage.tsx:768` + `SelectedClassCard.tsx:273`: the `errors:STALE_VERSION` message is lost against a real api. The card is keyed by `${selected.id}:${selected.version}`. On a 409 `STALE_VERSION` it sets its local `error` and calls `onReload()`. The refetch brings back a higher `version`, so the key changes, the card remounts and the error message disappears. The admin's edits are also dropped without a word. `INVALID_STATE` has the same problem, because a state change comes with a new version. Step 3 asks for «refetch + `errors:STALE_VERSION`».
   - **Why the test passes:** the T-06-28 test «R-06-09 saves the diff… STALE_VERSION» overrides PATCH to return 409 but leaves the server version unchanged. The key stays the same and the test cannot catch the bug.
   - **Fix:** raise these errors through the page-level `feedback` toast, or key the card by `id` only and reset the values on purpose when the version changes. Make the test's override also bump the mock version, e.g. do a real PATCH first and then send the old version.
2. **minor** `CancelClassModal.tsx:46-47,112,189`: when a class has a waitlist but no bookings (`bookings.length === 0`, `waitlistCount > 0`), the full D4c modal opens anyway. That part is correct (S06 R-06-10: the text is required if `waiting > 0`). But the text then reads «Aquesta classe té 0 alumnes inscrits…» and the button «ANUL·LA I AVISA ELS 0 ALUMNES». Nothing covers this case. **Fix:** use a waitlist-only intro and button, or count `bookings + waitlistCount`, and list the new texts as proposed literals.
3. **minor** `CalendarPage.tsx:287-291` + `calendar-shared.tsx:154`: for INSTRUCTOR the parameters are never loaded, so `defaultCalendarSettings` applies (`levelsEnabled: true`). With `levels.enabled=false` the read-only card still shows the «Nivells» chip (R-06-15). Assumption 7 in the report says this, but the report does not name the R-06-15 break. The report also admits that R-06-15 has no D4 test (no «+e» without `WAITLIST`, only `BLOCK` without `FREE_TRAINING`, levels chip hidden).
4. **minor** `RingBlockDrawer.tsx:85,96-97` (also `CreateClassDrawer.tsx:96`): there is a hard-coded fallback date `"2026-08-10"` in product code. `from`/`to` start from the time options of that Monday and are not reset when the typed date falls on another weekday. `startOptions`/`endOptions` then just add the stale value to the list. A Saturday block can go out with Monday's 07:00, which the server rejects with `OUTSIDE_OPENING_HOURS`. **Fix:** use the club-local today as the fallback, and clamp or reset `from`/`to` when `isoDate` changes.
5. **minor** `RingBlockDrawer.tsx:81,306-321`: editing an existing `RESERVATION` block while `FREE_TRAINING` is off leaves `kind` with no matching `<option>`. The select shows «Bloqueig» while the state stays `RESERVATION`. Real data can reach this state if the module is switched off later. **Fix:** always include `block.kind` in `kinds` in edit mode.
6. **minor** `SelectedClassCard.tsx:340-346,370-380`: the ring and instructor selects list active items only. When a class has an inactive ring or instructor, or no instructor, the `<select>` shows the first option while the state holds another value, so the card shows something different from what [ACCEPTA] would send. **Fix:** add the current value as an option, as `hourOptions` already does for the time.
7. **minor** `SelectedClassCard.tsx:280-289`: the «Exempta…» toggle calls `onSaved`, which reloads the class. If the api bumps `version`, the card remounts and silently drops chip edits that were not saved yet. Disable the toggle while `changed` is true, or save the edits first.
8. **nit** Step 7 asks for E4-W01's `ClassForm` in [Crear classe]. The drawer reimplements the fields instead (Assumption 4). The deviation is disclosed and argued, but the organizer should accept it explicitly. It also duplicates the validation rules of E4-W01's `ClassForm`.
9. **nit** `CalendarPage.tsx:803-805`: for a week that is neither CURRENT nor NEXT, the validation summary's `weekLabel` falls back to `calendar.week.select`, which is an accessibility-only label («Setmana»). The visible text is acceptable, but it is a proposed literal the report does not list for this use.
10. **nit** Mock gap: the MSW handlers never return `RING_HAS_BOOKINGS` for PATCH `/class-sessions`, POST `/class-sessions` or `/ring-blocks`. The `cancelBookings: true` confirmations (card modal, create drawer, block drawer) are therefore never exercised by Vitest or Playwright. Step 11 does not require it, but the Definition of Done's «ring blocks with conflict handling» covers only `RING_BLOCK_CONFLICT`.
