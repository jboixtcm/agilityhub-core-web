# Review E8-W02 — needs changes

## Findings

1. **major** `apps/clubs/src/inactivity/InactivityPage.tsx:86` — Overlap recovery ignores `details.periodId` and selects the first live period. With two disjoint live periods, the form can load—and subsequently PATCH—the unrelated period. Reproduced with conflict ID `conflict`: the next PATCH targeted `older`. This leaves round-3 point 6 incomplete (S13 R-13-02, §6). Select the returned conflict ID explicitly, preserve that selection in the link, and test multiple live periods.

2. **major** `apps/clubs/src/inactivity/InactivityPage.tsx:289` — Changing the start month can leave an invisible, invalid end month in state. Selecting end `2026-11`, then start `2026-12`, makes the dropdown display the empty option while submission still sends `toMonth: "2026-11"`. This contradicts the displayed selection and R-13-02’s range constraint. Clear or adjust the end explicitly when the start overtakes it; test the rendered selection and actual request body.

3. **major** `apps/clubs/src/billing/InvoicesPage.tsx:269` — Card recovery still depends on having a receipt. With `paymentMethod.invalid = true` and zero receipts, `items[0]` is undefined and the banner disappears; the same dependency exists in `ProfileLifecycleSection.tsx:45`, including when its receipt request fails. Conversely, `.find()` considers any historical failed CARD receipt, whereas step 3 specifies the **last** receipt. Decouple the recovery condition from receipt context, support approved copy when no receipt month exists, and restrict the fallback to the latest receipt. Add empty-list, failed-read and historical-failure regressions.

4. **major** `apps/clubs/src/inactivity/InactivityPage.tsx:149` — The new end-month horizon remains an arbitrary limit. An ACTIVE open period starting `2025-08`, with proposed month `2026-10`, offers ends only through `2027-10`; `2027-11` remains unavailable. Selecting the last option does not extend the choices. Round-3 point 2 explicitly requires access to any valid future end. Use an extensible month selector or another control without this unsupported cap, and test beyond the calculated boundary.

5. **minor** `apps/clubs/src/inactivity/InactivityPage.tsx:125` — A failed replacement preview silently retains the previous interval’s booking warning. Reproduced after changing months: the old count remained visible, no error appeared, and submission stayed enabled. Step 6 and S13 R-13-06 require the warning to reflect the selected interval. Associate previews with their requested range, invalidate stale results, and expose a failure/retry state instead of presenting the old count as current.

6. **minor** `packages/api-client/src/mocks/member-billing-handlers.ts:43` — Created inactivity periods and leave requests persist only in module memory. Actual navigation uses `window.location.assign`, which reloads the application and recreates these fixtures. Therefore the return-to-profile persistence required by round-2 point 7/#14 remains incomplete. `InactivityPage.test.tsx:285` substitutes a navigation spy and remounts within the same runtime, so it does not prove the reported browser flow. Persist mock state across navigation with tenant/scenario isolation and test creation followed by the real profile navigation.

7. **minor** `packages/api-client/src/mocks/fixtures/inactivity.ts:45` — The leave fixture substitutes `LEARNT_ENOUGH` and `PERSONAL` for the specified `LEARNED_ENOUGH` and `EXTERNAL` keys. These differ from S13 §13 and `CATALEG_PARAMETRES.md`’s `leave.reasons`; permissive mock submission hides the mismatch. Use the catalog keys and assert the submitted `reasonKey`, including rejection of an unknown reason.

8. **minor** `apps/clubs/src/billing/InvoicesPage.tsx:300` — `MODULE_DISABLED` renders “Encara no tens cap rebut,” incorrectly presenting unavailable billing as an empty receipt history. Detail loading also reduces this response to a generic failure. Step 2 explicitly requires the shared module-off state even when navigation normally hides the route.
