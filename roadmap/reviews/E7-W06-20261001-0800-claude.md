2. **minor** `packages/api-client/src/branding-cache.ts:130-144` (A4) — after 4 s the live read is **aborted**, not left to finish in the background. This also affects production, not just the e2e dev proxy.
   - On a slow network or a cold-starting core, a returning user runs the whole session on the cached branding: theme, locales and the `modules` that gate routes and menus (AGENTS rule 3).
   - The cache is not refreshed in that session, so while `/branding` keeps taking more than 4 s, every load starts stale.
   - **Suggested:** at the limit, resolve with the cache but let the request finish and `writeCachedBranding`, so the next load is fresh. Add a unit test that a late answer still updates the cache.
3. **minor** `packages/api-client/src/preferences-saver.ts:202-224` (step 4, Q3) — after the post-failure `GET`, the page and the outbox disagree.
   - The page shows what the api holds, e.g. X = false, while the outbox still holds the failed choice, X = true.
   - If the user then leaves without touching anything, `leave()` sends nothing and `kept(undefined)` is never called. The next visit within 5 min `take()`s the entry and silently PUTs X = true, which the user last saw as false.
   - This follows step 4 to the letter, so it is a spec gap rather than a code bug. The organizer should rule on Q3 before E7-W03. Options:
     - (a) after the `GET`, re-apply the kept patch as a visible queued change, so the page shows and retries the latest choice;
     - (b) once the page has shown the api's value, treat that as what the user accepted and clear the entry.
