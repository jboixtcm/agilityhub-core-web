## Findings

1. **minor** `packages/api-client/src/preferences-saver.ts:431-438` — **A refusal drops every kept value that was in the refused body, not only the value the api refused.**
   - **Sequence:** an earlier visit's departure kept `PERSONAL=false`.
     - The next visit adopts it (`adopt` → `held`, queued).
     - Within the 300 ms pause, the member picks a reminder option the api refuses. The same happens if a parked choice is merged into the member's next change (`:459-466`, then `flush`).
     - One `PUT {emailByCategory:{PERSONAL:false}, reminderMinutesBefore:240}` is answered `422 INVALID_REMINDER_OPTION`.
     - `withoutRefusedValues(held, body)` removes `PERSONAL` as well, because it has the same value in the body.
     - Result: `kept(undefined)` clears the outbox and the page shows the api's `PERSONAL`.
   - **Why it matters:** Round 2 point 1 says "only a 2xx for that choice, or a new choice for the same preference, frees it; `kept(undefined)` never follows a failure". R2-A3 reads a 4xx with the api's body as an answer, not a failure, and still asks for confirmation. Even under R2-A3, a valid kept choice is lost only because it travelled in the same body as the refused value.
   - **Suggested fix:**
     - Drop only the preference the refusal names: `INVALID_REMINDER_OPTION` → `reminderMinutesBefore`, `CHANNEL_NOT_ALLOWED` → push, otherwise `details.field` when the api sends it.
     - Keep the whole-body drop only when the refusal cannot be tied to one preference.
     - Add a test with a mixed body.
     - The organizer needs to rule on R2-A3 either way.

2. **minor** `packages/api-client/src/preferences-saver.ts:353-361` together with `:459-466` — **A kept choice that already got its own 2xx is shown again as pending and stays in the outbox.**
   - **Cause:** `held` is freed only when the *latest* request gets a 2xx and nothing is queued.
   - **Sequence:**
     - `adopt(A)` → `PUT A` is out.
     - The member changes B, another preference. Its `flush` is skipped because a request is out, so `queued={B}`.
     - `A` answers 2xx: `latest.confirmed` and the api holds A. But `held` is not freed because `queued` is not empty.
     - `PUT B` is sent and fails with a network error.
     - `queued = merge(held=A, {})` and `parked = true`.
   - **Result:** A is already saved, yet the page shows it as an unsent pending change and it stays in the outbox. The departure or a visit within 5 minutes sends A again, which can overwrite a change made elsewhere in the meantime. That is exactly the risk the 5-minute limit exists for.
   - **Why it matters:** this breaks step 2 ("the outbox entry goes only when that choice gets a 2xx") from the other side: the entry outlives its 2xx.
   - **Suggested fix:**
     - On a 2xx of a request sent alone with nothing out since (`alone && pending.length === 0`), remove from `held` the values that body carried. This mirrors `withoutRefusedValues`; call `kept(rest | undefined)`.
     - Add a test for this sequence.
