## Findings
1. **minor** `apps/clubs-admin/src/billing/BillingPage.test.tsx:1550-1556` — the check after «Flush the replacement detail's state/effect chain» doesn't test what its comment says.
   - The preceding `waitFor` only proves that MSW's handler was *entered* for detail read 3. The response still has to go through fetch, MSW and the `.then`, which takes more than two `Promise.resolve()` turns. So when the code checks `expect(periodReads).toBe(2)`, the component almost certainly hasn't processed read 3 yet.
   - The red proof works today only because the old code's loop drives the counters past `(2, 3)` before `waitFor` samples them, so `waitFor` times out (`51`: 15 s timeout; `52`: counter > 2,100). That catch depends on scheduling. If a `waitFor` check (MutationObserver or interval) happens to sample exactly `(2, 3)`, the old code would get past both assertions. Releasing `refreshedPeriod` then ends the loop, and the old code would pass.
   - This is the timing dependence round 2 asked to remove (E108 point 1, «asserted without wall-clock waits»).
   - Fix: wait until read 3's result is actually applied before the «still 2» assertion. One way is to make read 3 return a detail with a marker the UI renders and `findBy…` it. Another is to hold read 3 behind a third promise, release it, await its handler's resolution plus a native macrotask, and only then assert `periodReads === 2`.
2. **nit** `BillingPage.test.tsx:1489-1504` — the `setTimeout` spy returns the constant `5_000` as the timer id but doesn't stub `clearTimeout`.
   - The effect cleanup at `BillingPage.tsx:342` therefore calls the native `window.clearTimeout(5000)`. That can cancel an unrelated real timer that happens to have id 5000 (for example, a Testing Library `waitFor` interval in a long file).
   - Fix: also spy on `clearTimeout` and ignore the sentinel, or return a unique object or symbol id.
