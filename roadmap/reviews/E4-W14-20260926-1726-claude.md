## Findings
1. **minor** `apps/clubs-admin/src/activities/ActivityPage.tsx:528-537` (`saveErrorTargets` via `failSave`) — the UI side of the new mock `PATCH` refusal (`packages/api-client/src/mocks/activity-handlers.ts:780-785`) marks only one field.
   - **What happens.** Both time selects offer «—» (`:1244`, `:1264`). An admin can clear «Hora d'inici» and «Hora de final» on the published Torneig and click [DESA]. The mock (like the api) answers `422 ACTIVITY_INCOMPLETE` with two `fieldErrors`. `saveErrorTargets` returns only `fields[0]`, so only «Hora d'inici» is marked, with the generic `errors:ACTIVITY_INCOMPLETE` («Completeu l'activitat abans de continuar.»).
   - **Why it matters.** `publishWith` (`:647-657`) handles the same code by marking every field «Cal per publicar» and showing «Falten dades…» (R-07-04: «marks every empty field»). No Vitest covers the save path of this new branch.
   - **Fix.** In `failSave`, handle `ACTIVITY_INCOMPLETE` the way `publishWith` does: every `fieldErrors` entry gets `requiredToPublish`. Add a Vitest for [DESA] on the published Torneig with both times cleared.

2. **minor** `packages/api-client/src/mocks/fixtures/activities.ts:~276-300` — «Lliga social» (the executor's open question) is now a published activity the mock itself refuses to edit.
   - **The state is impossible.** The fixture is `PUBLISHED`, has every ring and has no `endTime`. T-07-03 forbids that («pistes sense `endTime` → `ACTIVITY_INCOMPLETE`»), and the core's seed has 9:00–14:00 (visible in `D7-publica-sense-hores-core-1280.png`).
   - **What round 2 adds.** `incompleteFields(next)` runs on every `PATCH` of a `PUBLISHED` activity, so under `VITE_MOCK` *any* edit of this row is `422 {endTime}`, even one that only changes `internalNotes` or the title. That breaks the fixed convention «Mocks behave like the api».
   - **Fix.** Accept the executor's proposal: `endTime: "14:00"`. Step 3 (R-07-13) already moves 04/D7 rows to start–end, so the mockup's «9:00» no longer holds anyway.

3. **nit** `packages/api-client/src/mocks/activity-handlers.test.ts` › «E4-W14 round 2 R-07-04 a published activity with rings stays publishable…» — organizer round-2 item 1 names «clears the date or a time».
   - The test covers `endTime`, both times and `registrationFrom`, but never `date: null`.
   - The mock does refuse it through `incompleteFields`, but nothing pins that down.
   - **Fix.** Add the `{date: null}` case.

4. **nit** `ActivityPage.tsx:704-717` — the windowless branch sends a real `POST …/publication` (`notifyEmail: false`) with no confirmation dialog.
   - It is safe only because R-07-04/T-07-03 guarantee a 422 for rings without a date or hours. If the api ever accepted such a draft, it would publish silently, without the confirm or the e-mail choice.
   - **Fix.** Say so in the doc comment. Better: if the call unexpectedly succeeds, show the normal confirmation first instead of publishing.
