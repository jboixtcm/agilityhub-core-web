## Findings
1. **minor** `e2e/core/e9-core.spec.ts` (`newClassSlots`, the `free` list: `[first, first + 1, first + 2, 17, 19]`): when today's earliest allowed hour (`first = hour + 2`) is later than 19, the fixed 17 and 19 slots stay in the list.
   - **Failure:** in a run at 20:00 or later, the first two "free hours" today are 17:00 and 19:00, which are already past. The test creates classes in the past (`POST /class-sessions`), the seat hold or booking then fails, and two of the three one-off tries are wasted. On a Sunday evening the 07 leg then fails even though a valid slot logic would have said so up front.
   - **Why it matters:** round-2 point 3 made the leg mandatory, so how reliable `e2e:core` is now depends on the time of day the run happens.
   - **Fix:** for `offset === 0`, keep only `start >= first`. Optionally, log "no slot left this week" before trying.
2. **minor** `e2e/core/e9-core.spec.ts` (`archivePlacement`, `deleteGeometry`, and the bare-ring branch of `tryCandidate`): the undo of a bare ring's geometry and placement never ran against the core in round 2. The final run's undo has only 4 steps: roles, class, booking and plan.
   - R-16-04 says the geometry can be deleted only when there is no `Placement` or ACTIVE `RingSetup` (otherwise `409 RING_GEOMETRY_IN_USE`). Nothing shows that an ARCHIVED placement doesn't count.
   - If it does count, `afterEach` turns a passing run red the first time the bare-ring path is taken. That path is exactly what round-1 attempt 6 needed.
   - `archivePlacement` also re-PUTs the placement without `name`, `displayName`, `activityId`, `mode`, `sizes`, `grades`, `scheduledAt` or `warningThresholdM` (`PlacementUpdateRequest`). That is harmless for the test's own placement, but a full-replace PUT nulls them.
   - **Fix:** exercise the path once, e.g. a run with the planned ring forced to a bare one, and attach its `e9-core-undo.json`. Also copy the optional fields through.
3. **minor** `e2e/core/e9-core.spec.ts` (`plannedFrom07`, step 1): the LIVE build session started from 07, which phone B also joins, is neither finished nor recorded anywhere.
   - The `Undo` doc comment says each step is undone "so the next test of the stage (or a retry) finds the seed's preconditions". An open session on the planned placement is left behind until P9 closes it after 12 h (R-16-11).
   - `finish` would create a `RingSetup` and break the "ring with no setup" precondition, so this may be the right trade-off. But it should be stated rather than implied as covered.
   - **Fix:** say so in the comment and in the `e9-core-undo.json` note, or abandon the session if the api offers a way.
4. **nit** `apps/clubs/package.json:39`: `"test": "vitest run && node --test ../../scripts/check-clubs-bundle.test.mjs"` sends any extra arguments to `node --test` instead of Vitest.
   - **Failure:** `pnpm --filter clubs test src/today/TodayPage.test.tsx` runs the whole Vitest suite, then asks `node --test` to run a `.tsx` file.
   - **Fix:** use a separate `test:bundle-check` script that `test` chains, or run the node test from a root/turbo task.
5. **nit** `turbo.json`: `scripts/check-clubs-bundle*.mjs` sit outside `apps/clubs`, so editing them does not invalidate the locally cached `clubs#test` / `clubs#build`. CI has no turbo cache, so CI is not affected. **Fix:** add `inputs: ["$TURBO_DEFAULT$", "../../scripts/check-clubs-bundle*.mjs"]` to the clubs tasks, or add the files to `globalDependencies`.
6. **nit** `roadmap/evidence/E9-W05/core-registrat-375.png`: the re-captured file (44.7 KB → 31.0 KB) shows an empty grey plan frame under «Registrat com a muntat». The capture at `e2e/core/e9-core.spec.ts:485-486` fires on the success text, before the plan or photo has rendered. This is one of the screenshots for Josep (step 3). **Fix:** wait for the plan's canvas or image before `screenshot()`.
7. **nit** `packages/api-client/src/ring-setups.ts:25`: the ADMIN-only fallback always puts `agilityhubLevel` in `levelLabel`, even when the setup has club `levelIds`.
   - The api's `/me/ring-setups` would send the club levels' codes, so for the same setup D12 reads «nivell Mitjà» for an ADMIN and «nivell C–D» for an INSTRUCTOR.
   - The comment documents it, and it is better than no level. Worth one line under Assumptions so the organizer accepts it explicitly.
