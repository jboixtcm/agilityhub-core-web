# Review E11-W01 — needs changes

## Findings

1. **major** `apps/clubs-admin/src/census/CensusRecordPage.tsx:1313`: «Descarrega les dades (RGPD)» is shown during a support access.
   - S17 R-17-10 closes «totes les exportacions de dades personals» to the support token with `403 SUPPORT_RESTRICTED`. E10-W03 already hides the header exports entry when `session.me?.support !== undefined` (`App.tsx:750`, and the same gate at `SupportAccessesCard.tsx:107`).
   - The new button only checks `erased`, so a support session gets a button that can only fail. AGENTS rule 3 says no dead actions.
   - Fix: hide `MemberDataExportButton` under a support session, and add a test using the `adminSupportAccess` scenario.

2. **major** `apps/clubs/src/notifications/actions.ts:19,49` + `apps/clubs/src/profile/DataExportCard.tsx:23`: a member who closes the tab cannot get back to a READY package from the app.
   - N-50 «Les teves dades estan a punt» is a MEMBER notification on APP+EMAIL with action `OPEN_EXPORT` (`CATALEG_NOTIFICACIONS.md:95`; R-14-13's example flow is built on it). `feedActionHref` still classes `OPEN_EXPORT` as back-office and returns `undefined`, so the in-app card opens nothing.
   - The job id is kept only in `sessionStorage`, which a closed tab or a fresh PWA launch loses. A new request then hits `422 DATA_EXPORT_TOO_SOON` for 24 h.
   - Result: Step 2 («the export job, its state and the download») only works if the tab stays open.
   - Fix: route `OPEN_EXPORT` to `/perfil` in the member app (seeding the card from `params.jobId` when present). Add a test for it.

3. **minor** `apps/clubs/src/profile/DataExportCard.tsx:167`: a FAILED job shows the raw server text `job.error.message`.
   - That text is English, even in a `ca` UI. AGENTS rule 4 says error codes map to i18n.
   - `ExportError` has a `code`. Use `t(\`errors:${job.error.code}\`, {defaultValue: t("auth:profile.dataExport.failed")})`, as `ExportsDrawer` does for its download errors.

4. **minor** Tests and the CHANGELOG cite **T-14-30** for the consent history (`MemberPrivacyCard.test.tsx:128`, `privacy-handlers.test.ts:103`, both `privacy.spec.ts`, `e11-core.spec.ts:190`).
   - In S14 §11, T-14-30 is something else: no real emails in the seed, the processors list comes from club config, and no non-technical cookie.
   - None of those tests asserts any of that. Only R-14-18's "consentiments consultables" clause applies.
   - Fix: rename them to R-14-18 (or a WP-14-G id) so the test-by-rule table is not misleading.

5. **minor** Copy was invented without being flagged (AGENTS rule 1).
   - S14 §13 #9 proposes only «Suprimeix les dades (RGPD)», «Descarrega les dades (RGPD)», «Descarrega les meves dades», «Supressió programada per al {data}», «Abonat suprimit #{n}» and «suprimit».
   - About 40 other `ca` strings were invented: «Privacitat i dades», «Historial de consentiments», «PROGRAMA LA SUPRESSIÓ», the four checks, the six block reasons, «Les meves dades», «Preparant el paquet…», «El paquet està a punt.», …
   - Yet the report says "Questions / catalog proposals: None".
   - The ready state could reuse N-50's catalogued «Les teves dades estan a punt».
   - Fix: list the new literals in the report for Jordi/Josep, as §13 #9 asks ("afegir al proper lot de mockups").

6. **minor** `MemberPrivacyCard.tsx`: three error paths leave the card in the wrong state.
   - **409 on the request (line 335):** after `409 ERASURE_ALREADY_REQUESTED` (another admin, or a stale view), the dialog shows the error and the card keeps offering «Suprimeix les dades (RGPD)». It should re-read `GET /members/{id}/erasure` and show the scheduled state.
   - **Failed initial GET (line 159):** a 500 or network error leaves `erasure` undefined, so the request button shows next to the alert, with no retry.
   - **409 MEMBER_ERASED (lines 335, 387):** neither the erasure calls nor `MemberDataExportButton` call the page's `onErased`, unlike the other D10 actions (E7-W06). The header actions stay live.

7. **minor** `MemberPrivacyCard.tsx:246`: BLOCKED and ERASING requests are both shown as «Supressió programada per al {date}».
   - A BLOCKED request is retried daily, and an ERASING one is already running. Neither is simply "scheduled".
   - The block reasons are listed, but the headline is wrong. Consider a distinct status line per `ErasureRequest.status`.

8. **minor** `MemberPrivacyCard.tsx:222`: non-LEFT members get no erasure text at all.
   - R-14-14 says «Un abonat ACTIVE que demana la supressió primer ha de tramitar la baixa (S13): la UI ho diu.»
   - The `memberNotLeft` key is only reachable through an API 422 that the UI never lets the admin trigger.
   - Fix: add a short note in the privacy card for ACTIVE/INACTIVE members, or record the reading of §2 «Peu (només abonats LEFT)» as an assumption.

9. **minor** Test gaps:
   - `DataExportCard`: no test for the FAILED or EXPIRED states, or for `NOT_FOUND`/`EXPORT_EXPIRED` clearing the stored job.
   - `MemberPrivacyCard`: no component test for 409 `ERASURE_ALREADY_REQUESTED`, 409 `INVALID_STATE` on cancel, a BLOCKED request with `blockReasons`, or the admin `DATA_EXPORT_TOO_SOON`.
   - The D10 admin data export is not exercised in any browser flow, mock or core.

10. **nit** `MemberPrivacyCard.tsx:74`: `deliverToMember: false` is hard-coded, so an admin can never trigger N-50 to the member. That may be intended, but it is an unrecorded assumption.

11. **nit** `DataExportCard.tsx:62`: polling runs every 1 s with no upper bound on a mobile PWA.
    - The E11 core run showed a job sitting QUEUED for more than 150 s.
    - Other screens bound their polling (R-12-13's two-minute stop with [Actualitza]); consider the same.

12. **nit** `DataExportCard.tsx:143`: the fallback filename `"dades-personals.zip"` is a Catalan literal in code. Likewise, «Estarà disponible durant 7 dies» hard-codes `memberDataRetentionDays`; `job.expiresAt` could be shown instead.

13. **nit** `CensusRecordPage.tsx:1277` vs `:1241`: the «suprimit» badge keys off `displayStatus.kind === "ERASED"`, while the actions key off `erased` (`erasedAt` or `erasedMeanwhile`). After a 409 MEMBER_ERASED mid-session, the actions disappear but the badge does not appear.

14. **nit** `e2e/core/e11-core.spec.ts:213-247`: if the UI leg fails after scheduling, the SCHEDULED request is left in place, because there is no `afterEach` cancel. That is harmless in a disposable stack, but E9-W05 set the precedent of undoing changes.

15. **nit** `packages/api-client/src/mocks/handlers.ts` (`GET /exports/:id`): the mock does not enforce that a member only sees their own jobs. T-14-17 has «Pau → 404», which the mock cannot reproduce.
