# Review E5-W01 — needs changes

The one major issue is small to fix but needs a wording decision. Everything else is minor or a nit. Evidence holds up: `05-turbo.log` 34/34, Docker e2e 42 + 48 + 1, and 10 PNGs are tracked in git.

## Findings

1. **major** `apps/clubs/src/booking/ConfirmPage.tsx:402-417` (+ `ca/booking.json` `confirm.limitDone`) — The limit-done variant of 29 tells the member something false in the most common case.
   - **What happens:** for a class in the current week (`details.week = CURRENT`), the note says «Aquesta setmana ja has fet dues classes amb la Duna. Podràs reservar aquesta classe a partir de diumenge 9 a les 20 h.» for a **Saturday 8** class. Sunday 9 is after that class has taken place. The same text is in `29-limit-375.png` and asserted in `confirm.test.tsx:243`.
   - **Why it is wrong:** `nextBookableAt` is the start of the next booking week (S08 §6). «aquesta classe» (B1) is only true when the limit reached is next week's (`week = NEXT`, max 1 → the class becomes current-week, max 2, on Sunday 20:00).
   - **Other gaps in the same note:** `limitDone` also ignores `details.week` (always «Aquesta setmana») and `details.unit` (always «amb la Duna», even with `unit = MEMBER`, where the classes may have been with another dog). `limitNote` already handles both.
   - **Fix:** render the `nextBookableAt` sentence only when `details.week === "NEXT"`, and add `week`/`unit` selects to `limitDone`. Ask @organizer/@jordi for the current-week wording: the original mockup text «Podràs reservar per a la setmana vinent a partir de …» was correct for that case, so B1 needs a current-week variant.

2. **minor** `apps/clubs/src/booking/HomePage.tsx:31-32` + `ReservationRow.tsx:58-61` — A member with a single dog sees « · amb Duna» on every row.
   - **What happens:** `dogId` stays `null`, so `/me/home` answers the «Tots» view. The real api (`MemberHomeQuery.java:45`) then fills `dogName`, while the lone chip is drawn as pressed.
   - **Why it is wrong:** the 03 mockup note (V3) says «el nom del gos només es mostra amb més d'un gos seleccionat», and step 2 says « · amb {dogName}» renders only in the «Tots» view.
   - **Test gap:** the single-dog test (`home.test.tsx:129`) never checks the rows.
   - **Fix:** when `data.dogs.length === 1`, drop `dogName` from the rows or request with that dog's id, and assert it in the test.

3. **minor** `packages/api-client/src/mocks/fixtures/bookings.ts:466-467` (report, assumption 1) — The mock drops ACTIVITY rows when a dog is selected. The published api keeps them (`MemberHomeQuery.java:22` «Activity registrations belong to the member … so the dog filter keeps them»; lines 62-66 add them regardless of `dogId`).
   - **Consequence:** `home.test.tsx:118` («Toby → Encara no tens cap reserva») encodes behaviour the real core will not have. E5-W04 will see activity rows under every dog.
   - **Fix:** align the mock with the api and adjust the test (for example, a dog with no rows under a scenario without activity registrations).

4. **minor** `apps/clubs/src/booking/BookingDetailPage.tsx:151-208` — The green or yellow note appears for **any** booking in `CANCELLED`/`CANCELLED_LATE` with a `cancellation`, not only after the member cancels on this page.
   - **Swap case:** a booking cancelled by a swap is `CANCELLED` with `late=false`. The mock even sets `byRole: "MEMBER"` (`booking-handlers.ts:208-214`). Opening it later from the history (25) says «Anul·lació feta dins el termini establert: pots reservar una altra classe per aquesta setmana.», which is false: the swap used that slot.
   - **Other cases:** the same applies to SYSTEM cancellations (payment timeout, inactivity) and to old cancellations opened weeks later.
   - **Spec:** step 6 ties the notes to the result of the page's own `POST …/cancellation`.
   - **Fix:** keep the response's `late` in local state after `cancel()`, and show the note only then. Otherwise show just the state chip.

5. **minor** `apps/clubs/src/booking/BookingDetailPage.tsx:141-146` — «Reservada per {name}» is decided by comparing the first word of `me.account.name` (the global ID account) with `bookedBy.displayName` (the api's member first name).
   - **Failure cases:** a different spelling or an account name like «L. Serra» makes the member's own bookings read «Reservada per Laura …». Two group members with the same first name make the other member's bookings read «Reservada el …».
   - **Status:** the executor already raised this (question 3). The organizer should open the api follow-up (`BookedBy.self` or `accountId`) rather than accept the heuristic as final.

6. **minor** `apps/clubs/src/booking/ConfirmPage.tsx:105-116` — Step 4 says «a fresh `Idempotency-Key` per attempt»; the code keeps one key per payload, so a retry after a network error or 5xx resends the same key.
   - **Api side:** it documents «Idempotency-Key = seatHoldId» (`BookingsController.java:124`) but accepts any UUID. The per-payload choice is defensible (it lets the api deduplicate, and a different swap choice cannot hit `IDEMPOTENCY_KEY_REUSED`).
   - **Action:** it deviates from the task text. The organizer should confirm it (question 4) and fix the step wording.

7. **nit** `apps/clubs/src/booking/BookingDetailPage.tsx:159-160` — The 07 «Falten menys de 4 hores» warning compares `startsAt − threshold` against the raw device clock. The same flow's countdown uses `serverNow` on purpose (T-08-36), so a skewed device shows or hides the warning wrongly (the api's `late` still decides). If `Booking` ever carries `serverNow`/`cancellableInTimeUntil` (question 1), use it here.

8. **nit** `apps/clubs/src/booking/ConfirmPage.tsx:353-360` — With `PAY_TO_BOOK` **and** a swap, the button shows only «ANUL·LA … I CONFIRMA …». The price and «PAGAR» disappear, but the 201 still redirects to Checkout, so the member is not told they are about to pay. Show the price note in the swap variant too, or combine the two labels (a literal to propose).

9. **nit** Two test names claim more than they assert:
   - `book.test.tsx:113` («… WAITLIST off reads «Completa» inert, SINGLE_CLASS adds the price») asserts only ACTIVITIES/PACKS off.
   - `detail.test.tsx:77` («… without it no warning and the late note has no number») asserts only «90 minuts».
   
   Both behaviours are covered by other tests; rename these to match what they check.
