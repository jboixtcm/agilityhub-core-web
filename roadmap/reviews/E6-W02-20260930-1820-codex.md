# Review E6-W02 — needs changes

## Findings

1. **major** `packages/api-client/src/followup.ts:265` — Uploaded file keys are cached indefinitely. If uploading succeeds but task creation fails, retrying after the grant’s five-minute expiry repeatedly submits the expired key; the API’s `AttachmentService.claim` rejects it with `INVALID_STATE`. The form cannot recover without reselecting files. This breaks the attachment flow required by R-10-11 and step 3. Track grant expiry and renew uploads after a definitive rejection, while preserving the original payload/key for unanswered submissions. Add an expiry-aware retry test; the current MSW handler does not enforce grant expiry.

2. **minor** `packages/ui/src/tasks-panel.tsx:927` — Mixed file selections silently lose rejection messages. `AttachmentPicker` calls `onReject` for invalid files, then `onPick` for accepted files; the immediate attachment action clears `refusedFile`. Reproduced with an accepted JPEG plus a rejected executable: the JPEG was submitted and no alert remained. This violates step 2’s validation feedback requirement. Preserve all rejected-file messages through uploads of accepted files, and test this through `DogFollowupEditor`.

3. **minor** `apps/clubs-admin/src/instructor/StudentRecordPage.tsx:334` — Escape from the task-deletion confirmation closes both the confirmation and D13’s editor drawer. Both overlays handle the same document-level key event, so cancelling deletion also discards unsaved task text, selected files and inline edits. Reproduced with the actual `Drawer`/`TasksPanel` composition. This violates the confirmation behavior and AGENTS rule 6’s keyboard interaction requirement. Only the topmost overlay should consume Escape; add a draft-preservation regression test.

4. **minor** `packages/ui/src/tasks-panel.tsx:621` — A failed deletion keeps the confirmation modal open but renders its error behind it in the tasks panel. Reproduced with a refused delete: the dialog remained open with no error inside it. Users, especially those using assistive technology, receive no explanation within the active modal. Step 3 requires errors by code. Show the translated failure inside the confirmation, or close it and move focus to the visible error.
