# Review E8-W02 — needs changes

## Findings

1. **major** `apps/clubs/src/payments/CheckoutReturn.tsx:36` — Anonymous signup polling never sends `X-Signup-Token`, which the adopted OpenAPI requires. Real signup returns therefore receive `401` instead of confirming payment; MSW accepts them unconditionally. Pass the signup capability into this component and test the required header. · Task step 4, S12 §6.

2. **major** `apps/clubs/src/SignupPage.tsx:2575` — The new retry action returns to the payment page after the existing sent-page effect deletes the draft, including `memberId` and `signupToken` (`2671–2672`). It cannot resume checkout for the existing signup. Preserve the submission until payment is resolved and renew only the checkout attempt when retrying. · Task step 4, R-04-26.

3. **major** `apps/clubs/src/payments/CheckoutReturn.tsx:45` — Ten seconds of `PENDING`, or request failures, becomes “The payment session has expired” with a payment retry button. Elapsed polling time does not establish expiry; the payment may already have succeeded while its webhook is delayed. Stop polling with an unconfirmed state and reserve expiry/retry behavior for API `EXPIRED`. · Task step 4: webhook state is authoritative.

4. **major** `apps/clubs/src/billing/InvoicesPage.tsx:238` — Card recovery depends exclusively on finding a failed card invoice. `ProfileLifecycleSection.tsx:38` does likewise; `CensusRecordPage.tsx:1283` infers invalidity from any failed recent invoice plus the current CARD method. A detached card without a failed receipt gets no recovery action, while an old failure can falsely mark a replacement card invalid. Wire the actual invalid-card field through the contract and all three views. · R-12-22, steps 3/8, organizer message of 05-10.

5. **major** `apps/clubs/src/inactivity/InactivityPage.tsx:106` — Consultation selects cannot reliably represent existing periods. Start options begin at `earliestFromMonth`, excluding an ACTIVE period’s historical start; end options stop twelve months after that start, making a long-running open period impossible to end in a later valid month. Both ranges also hard-code thirteen options instead of using API bounds. Preserve existing values, support valid future ends, and report the missing API-bound contract. · R-13-01…04, step 6.

6. **major** `apps/clubs/src/inactivity/InactivityPage.tsx:138` — Every PATCH sends `fromMonth`, `toMonth`, and `comments`, and comments remain editable for ACTIVE periods. The contract allows an ACTIVE member to change only `toMonth`. Disable prohibited edits and construct PATCH bodies from permitted changes, preserving omitted-versus-null semantics. Add an ACTIVE-period request-body assertion. · R-13-04, ruling E85.

7. **major** `apps/clubs/src/leave/LeavePage.tsx:60` — A pending request displays `defaultDate` rather than its saved `requestedDate`, then disables the date field. Someone requesting departure next month sees today as the requested departure date when reopening the form. Initialize from `live.requestedDate` in consultation mode. · S13 §2, step 7.

8. **major** `apps/clubs-admin/src/census/MemberBillingBlock.tsx:213` — Pack adjustment rows show no dog identity; they display only plan name, balances, and expiry.
