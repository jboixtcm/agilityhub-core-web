## Findings
1. **minor** `e2e/core/e4w16-core.spec.ts:484-501` and `:398-419` — The "pending real-core proof" fallbacks are still in place. Step 1 passes when `launchUrl` is missing, and step 10 passes when the first `PUT /me/password` answers `401`.
   - **Why it matters:** image `90855aa` now carries api E5-T27. If the api regresses (drops `launchUrl`, or stops honouring the one-time RESET skip, E49), the stage still passes green with only an annotation. Steps 1 and 10 are the reason this stage exists (task "Fixed conventions").
   - **Fix:** make both branches fail now. Alternatively, gate them on an explicit env flag or the image revision.

2. **minor** `packages/auth/src/auth-client.ts:571` — A handoff grant that fails still falls back to the cookie. This covers a refused code, and also a 5xx or offline answer on `/oauth2/token` itself. In both cases `pendingHandoff` stays null, so the waiting `restoreSession()` goes on to the cookie refresh ("the usual restore follows").
   - **What the user sees:** the tab shows «Aquest enllaç ja no és vàlid» on 01. Meanwhile `SessionProvider` silently signs in whoever holds the club host's refresh cookie. That is often the admin's own member session, with no banner.
   - **Why it matters:** round-2 #1 closed this for a failing `/me`, but E47's intent (the impersonation tab never becomes the admin's own session) applies to the same tab here too.
   - The step 1 test at `apps/clubs/src/App.test.tsx:647` does not assert that no `refresh_token` grant is sent.
   - **Fix:** once `exchangeHandoff` has been attempted, mark the tab `ended` (no cookie until the user signs in). At minimum, add an assert that no refresh grant is sent.

3. **minor** `apps/clubs-admin/src/App.tsx:655-663` — The new `pending`/`ended` handoff states live in the shared `AuthClient`, so they also apply to the back-office handoff (03b → `createHandoff("clubs-admin")`). The clubs-admin page has no UI for them, and no clubs-admin test covers them.
   - **Transient `/me` failure:** the page shows «Aquest accés al backoffice no és vàlid o ha caducat», which is wrong for a transient error, and offers no retry. The background retry later signs in, but the page stays on the error; the code also stays in the address.
   - **A 4xx from `/me`:** the admin tab is left `ended` and never reads its own cookie until a manual sign-in. Round 1 fell back to that cookie, which was harmless here because it is the same person.
   - **Token storage:** while the handoff is pending, a normal (non-impersonated) admin access token sits in `sessionStorage`. Assumption A1 only covered impersonation tokens.
   - **Fix:** either limit the no-cookie states to impersonation handoffs, or port the retry UI to clubs-admin and add a test.

4. **nit** `packages/i18n/src/locales/es/auth.json:42` — The new `activation.retry` reads «Volver a intentarlo». The same file uses «Vuelve a intentarlo» in `access.genericError`, which is shown right above this button, and in `onboarding.retry`. Align them, or reuse the existing key.
