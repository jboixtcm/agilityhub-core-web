# Review E8-W01 — needs changes

## Findings

1. **major** `apps/clubs-admin/src/billing/BillingModals.tsx:167` — The selected collection date disappears after an unanswered generation attempt. Reproduced in memory: `422 COLLECTION_DATE_TOO_SOON` → submit with `collectionDate=earliest` → `503` → retry sends **no collectionDate**. The changed payload also selects a different idempotency key, violating CONVENCIONS_API §7/E85. Persist the accepted date independently of the latest error; test that retries after network errors, `5xx` and `IN_PROGRESS` retain both payload and key.

2. **major** `apps/clubs-admin/src/billing/ManualInvoiceModal.tsx:100` — The member picker forces `status:eq:ACTIVE`, preventing adjustments for members who have left—for example, returning an overcharged cash payment after departure. R-12-19 and the published `POST /invoices` contract impose no active-member restriction; erased members are rejected separately. Remove this additional restriction and test an adjustment for a `LEFT` member.

3. **major** `apps/clubs-admin/src/billing/BillingPage.tsx:274` — A failed initial run-detail request silently prevents card-charge monitoring. Polling depends exclusively on `runDetail.status === "CHARGING"`; if that GET fails after charging, or when reopening a charging month, neither polling nor the “Actualitza” recovery control starts—even when the period response says `CHARGING`. This leaves receipts and counts stale, contrary to step 5/R-12-13. Start bounded monitoring from the period’s charging state and expose read failures with retry; cover an initial failed GET.

4. **minor** `apps/clubs-admin/src/billing/BillingPage.tsx:348` — Removing an ineligible receipt from the selection only changes a derived set; the underlying `selected` state retains its ID. Reproduced from the source: a selected receipt becoming `PAID` disappears from the displayed selection, then reappears when rows become empty during loading or pagination. A subsequent bulk payment includes that already-paid receipt and rejects the batch under R-12-16. Persist removals when fresh rows establish ineligibility and test payment in the drawer followed by pagination.

5. **minor** `apps/clubs-admin/src/billing/RemittancesPage.tsx:130` — Default saved views never apply on a bare `/facturacio/remeses` visit. The mount effect immediately writes pagination and fields into the URL; `useSavedViews` subsequently applies the default only when the query string is empty. This breaks the universal-list behavior required by step 9/CONVENCIONS_API §4. Preserve the initial bare URL until default-view resolution, as BillingPage already attempts, and test reopening a default view.

6. **minor** `apps/clubs-admin/src/billing/InvoiceDrawer.tsx:291` — Refetch failures are hidden once an invoice has loaded. After a refund or conflict triggers `refresh()`, a failed GET retains the old invoice while `loaded !== reload` disables its actions indefinitely. The error/retry branch only renders when `invoice === undefined`. Confirmed with an in-memory control-flow probe. Show refetch errors and a retry control alongside cached data; cover this recovery path in the step 7 tests.
