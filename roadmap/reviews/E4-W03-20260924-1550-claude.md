# Review E4-W03 — minor issues

Round 2 fixes all four points the organizer raised:
- **Invalid dates.** `parsePlainDate` checks that year, month and day survive a round trip. An invalid `?date=` falls back to the club's today and rewrites the address. There are tests for all four bad values.
- **Plain dates.** `formatPlainDate` formats in UTC and replaces every listed call site. The Kiritimati and Auckland cases would really have caught the old noon-UTC bug.
- **«Sense» column.** It now comes from the API, and the page no longer adds its own.
- **Mocks.** They now check role, impersonation and club, with negative tests.

The evidence logs exist and match the report: turbo `--force` shows 34/34 tasks with 0 cached, clubs 55 and clubs-admin 95 tests; e2e passed 29 + 1 + 25. Below are only the remaining points.

## Findings
1. **minor** `packages/api-client/src/mocks/day-grid-handlers.ts:109` — **The executor did not follow organizer point 4 on `GET /ring-blocks/{id}` for MEMBER.**
   - The organizer asked for 403 `FORBIDDEN`. The mock returns the redacted `RingBlockMemberView` instead.
   - The spec supports the executor's choice: S06 §6 row `/ring-blocks · /ring-blocks/{id}` says «MEMBER (redactat) … 200 (MEMBER: sense `note` ni `createdByName`)». `MATRIU_PERMISOS` says «R (com «Ocupada», sense qui)». The OpenAPI says «Staff or redacted MEMBER projection».
   - The executor flagged this openly (round 2, Question 1).
   - **Fix:** the organizer should confirm the redacted projection (my recommendation) or keep the 403. Either way it is a one-line change.
2. **minor** `packages/ui/src/day-grid.tsx:205` — **A cell whose `ringId` matches no column disappears without trace.** This happens, for example, when a class has `ringId: null` but the API sent no «Sense» column.
   - The new test (`apps/clubs/src/today/TodayPage.test.tsx:249`) feeds exactly this case: «Obediència» with `ringId: null`. It checks the headers but never says whether the class should vanish, so the data loss is implicit.
   - The contract (R-06-12, form D) makes this unreachable against a correct API. Still, a presenter silently hiding a class is a trap if the API ever sends a cell for a ring that is inactive or missing from the columns.
   - **Fix:** add an explicit `expect(queryByText("Obediència")).toBeNull()` with a comment that this is intended, or log a warning in development builds.
3. **nit** `packages/i18n/src/format.ts:125` — **`formatDateRange` can still shift a day when one end is a plain date and the other a timestamp.**
   - In that case it uses the club's zone, and `toDate` reads the plain date as midnight UTC. That is the same one-day shift R-06-14 forbids, in zones behind UTC.
   - No caller mixes the two today.
   - **Fix:** format each end in its own zone, or reject mixed input.
4. **nit** `apps/clubs/src/today/useDayGrid.ts:50-55` — **`initialDate` rewrites the address during render.** It calls `history.replaceState` from inside the `useState` initializer. The call is idempotent, so StrictMode's double render does no harm, but a side effect in render is fragile. **Fix:** move the rewrite into a mount effect.
5. **nit** `packages/api-client/src/mocks/day-grid-handlers.ts:71` — **The mock accepts any `view` value.** Anything other than `instructor` (`view=foo`, or no `view`) is served as the member view. S06 §6 lists 400 for bad input, and the mock already answers 400 for bad dates. **Fix:** answer 400 `VALIDATION_ERROR` for an unknown `view` too, so the mock stays faithful.
6. **nit** `apps/clubs-admin/src/planning/calendar-shared.tsx:106` — **`parseMaskedDate` checks the date twice.** Its second check (`new Date(`${iso}T12:00:00Z`).toISOString().startsWith(iso)`) repeats what `isIsoDate` → `isPlainDate` now guarantees. It also brings back the noon-UTC pattern round 2 set out to remove. **Fix:** drop the second check.
7. **nit** — **Follow-up for E4-W02, not a defect here.** The executor's round-2 Question 2 is real: `CalendarDayPage` (D4 day view) still derives «Sense» itself. Against the real `/day-grid`, which now sends its own «Sense» column, it would show two. It should be tracked as a follow-up on E4-W02 so it is not lost.
