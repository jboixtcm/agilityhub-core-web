# Review E3-W08 — needs changes

## Findings
1. **major** `apps/clubs-admin/src/dashboard/SignupEditDrawer.tsx:75-97, 136-165` and `packages/api-client/src/mocks/fixtures/signup-review.ts` (the `readmission` variant) with `handlers.ts` (the member PATCH that recomputes `submitted` from `member`): D2 is built on the wrong readmission model.
   - **What the api says.** The openapi text for `MemberSignupView.readmission` says «The LEFT record keeps its values until validation». The real core confirms it: `D2-readmission-core-1280.png` shows PERSONA with the old contact «pau.e3@example.test · +34 699000902», and only the new block has «Ara: +34 699000905». So `member` is the LEFT record. The `PATCH /members/{id}` description says that during a readmission, edits change the *submitted* values.
   - **What the mock does.** It puts the submitted values in `member` and derives `submitted` from it. The Vitest «an edit of the submitted phone updates the «Ara» value» passes only because of this. The real core does not behave that way.
   - **Result on the real core:**
     - the drawer opens with the LEFT values;
     - `memberPatch` sends whole arrays (`contactEmails`, `phones`) and the whole `address`. If the admin edits phone 2, the body carries the *old* phone 1, and the new phone 1 the applicant submitted is silently replaced;
     - the PERSONA card and WhatsApp use the old phone.
   - **Rules:** S04 R-04-06 (E38); AGENTS rule 5 (MSW handlers must behave like the api).
   - **Fix:**
     - for a readmission, build the person form, the card contact and WhatsApp from `readmission.submitted`;
     - make the mock keep `member` as the LEFT record and apply PATCH edits to `readmission.submitted`;
     - add a Vitest: during a readmission, editing phone 2 keeps the submitted phone 1.
2. **major** `apps/clubs/src/SignupPage.tsx:2474, 2582-2584, 2630-2638`: `leaving` is set on every same-origin step change and never reset.
   - With the production `location.assign`, a browser Back (common on mobile) can restore the departing document from the bfcache. That document still has `leaving = true`, so it shows «Carregant el formulari» with no way out except a reload.
   - The same happens if the navigation is aborted.
   - There is no `pageshow` or `unload` handling in `apps/clubs/src`.
   - **Fix:** on `pageshow` with `event.persisted`, clear `leaving` and re-read `path` from `location`. Add a test that dispatches a persisted `pageshow`.
   - Not reproduced in a browser; this comes from reading the code.
3. **minor** `SignupPage.tsx:1933-1941`: once the signup is committed (`submission.memberId`), the card still shows the live `GET /signup` quote, not the frozen `SignupResult.upfront`.
   - Example: submit on 15-08 with a full month (total 160 €). Stripe checkout is cancelled, and the applicant retries on 16-08. The card now shows «(mig mes)» and a 130 € total, but 160 € is what gets charged (T-04-32, R-04-14 «congelat en enviar»).
   - **Fix:** keep `result.upfront` in the draft's submission and render it while committed.
4. **minor** `SignupPage.tsx:2305-2308`: every line concept except `PACK` is labelled «Entrada (1 gos)». `SignupQuoteLine.concept` also allows `FIRST_MONTH` and `ADDITIONAL_DOG_FEE`, which would get the wrong label.
   - **Fix:** map `ENTRY_FEE` explicitly, and label or skip the other concepts.
5. **minor** `e2e/core/e3-signup.spec.ts` (the `leftLookup` block, `if (leftMember?.idDocument == null) { writeFileSync(...) } else {...}`): the readmission check passes silently when no LEFT member is found.
   - Attempt 1 (`06-…-left-lookup-400.log`) exited 0 with the whole block skipped.
   - The same run always creates the LEFT member it needs (the rejected «Pau Rebuig E3»), so the lookup should be asserted (`expect(leftMember).not.toBeNull()`) instead of logged.
   - This case readmits an applicant rejected minutes earlier, not a seed member with a real `leftAt` history. The report says so; the organizer should know that the «D10 shows the original data» check covers only this case.
6. **nit** `SignupPage.tsx:1639-1646`: a maintenance plan with `entryFee.amountMinor = 0` still shows «Entrada a compte: 0,00 €». Step 5 says «a plan without an entry fee shows no entry line», and the `<= 0` guard at `:1627` does not cover this branch.
7. **nit** `handlers.ts` (`POST /signup`, `POST /me/dogs/signup`): the mocks do not enforce the two flags.
   - `requireDogDocumentAtSignup = true` without files should answer `422 DOG_DOCUMENT_REQUIRED` (R-04-08, T-04-13).
   - `leavePending` with `allowFamilyGroupPending = false` should answer 400 (T-04-16).
   - As it stands, the flags only exist as values in `GET /signup`.
8. **nit** `packages/ui/src/on-primary.test.ts`: the guard matches only the exact declaration `background(-color): var(--ah-color-primary)`.
   - It misses `color-mix(… var(--ah-color-primary) …)`, shorthand backgrounds with more values, and TSX inline styles.
   - Its claim that no component hard-codes white on the primary colour is therefore narrower than it reads.
