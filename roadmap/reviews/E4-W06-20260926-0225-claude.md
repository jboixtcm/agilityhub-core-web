# Review E4-W06: minor issues

## Findings
1. **minor (needs an organizer ruling)** `packages/i18n/src/locales/{ca,es,en}/admin-catalogs.json` `levels.progressionHelp`
   - **What is wrong:** the help text names the Cànic's own levels: «com Teràpia … «D i sup.»», «como Terapia … «D y sup.»», «such as Therapy … «D and up»». Every club would see this text, including clubs that have no Teràpia or whose first progression level is not D.
   - **Why:** this conflicts with AGENTS hard rule 2 (no club literal in locales). The executor copied the text as Step 1 and S05 §2 give it, and flagged the conflict (report Q2).
   - **Suggested fix:** use a generic wording, for example «Els nivells fora de la progressió no compten per a la descripció «… i sup.»». Or interpolate `{first}` from the club's first active progression level. The organizer should decide, then update S05 §2.
2. **minor** `apps/clubs-admin/src/catalogs/SettingsPage.tsx:471,508-528`
   - **What is wrong:** `progressionPending` holds a single level id. Toggle row A, then row B while A's PATCH is still in flight. A's `finally` sets `progressionPending(undefined)`, which re-enables B's switch while B's PATCH is still pending. A second click on B then sends B's old `version` and gets `STALE_VERSION` plus a list reload.
   - **Related:** `setProgressionError(undefined)` at the start of B's toggle also clears the error of A's PATCH.
   - **Suggested fix:** keep a `Set<string>` of pending ids, or disable every «Progressió» switch while any PATCH is pending.
3. **minor** `apps/clubs-admin/src/planning/TemplatesPage.tsx:1210-1216` (`queueRemoval`)
   - **What is wrong:** `patchGeneration` is bumped before the DELETE runs, even when the DELETE later fails. A class PATCH queued behind the removal is then dropped silently: `send` returns without throwing, so the #7 revert in `ClassForm.change` never runs.
   - **Consequences:**
     - If a «Treu de la plantilla» DELETE fails, a chip the admin clicked while it was queued stays on screen unsaved, with no error.
     - `removeBand` drops class PATCHes that have nothing to do with the band. The comment «built on the removed item» only holds for a class DELETE that succeeds.
   - **Suggested fix:** bump the generation only after a successful class DELETE, and not for band removals. Or make dropped sends reject, so the form puts the chips back.
4. **minor** `apps/clubs-admin/src/planning/TemplatesPage.test.tsx` (describe «T-06-26 E4-W06 …»)
   - **What is missing:** Step 5 #3 covers `removeClass` and `removeBand` and asks for one Vitest each. Only `removeClass` is tested. The `removeBand` path through `patchQueue` has no test.
   - **Suggested fix:** add the same held-PATCH test with «Treu la franja». Assert that the DELETE is sent after the PATCH answers, and that the drawer closes.
5. **nit** `e2e/core/d11-core.spec.ts:100-107`
   - **What is wrong:** the raw-key regex only catches `admin-settings:` / `param.` strings. An enum without a label falls back to `defaultValue: value`, which shows a raw code such as `EVENT_START`. The regex does not match that, and `<select>` option text is outside the scanned selector.
   - **Impact:** enum labels are guarded only by `check-parameter-keys.mjs`. That is acceptable, but the report's claim «D11 shows no raw key» is a little broader than what this test asserts.
6. **nit** Report §4 says «The script's allowlist follows the core».
   - **What is wrong:** `signup.onboardingFields` and `legal.maxPostpones` are in the core's `system` block (`d11-core-parameter-blocks.json` lines 150-157) but not in `systemOnly`. So the allowlist is the core's `system` block minus these two, which the script requires labels for.
   - **Impact:** harmless (the extra labels exist). The statement should be corrected, or the two keys added to the allowlist with a comment.
7. **nit** `apps/clubs-admin/src/catalogs/SettingsPage.test.tsx:77`
   - **What is wrong:** the describe carries no T-id (AGENTS rule 5).
   - **Suggested fix:** cite T-02-13 (the D11 test id), as the core spec does. S05 has no front-end test id for the «Nivells» card.
8. **nit** `packages/api-client/src/mocks/fixtures/catalogs.ts:113-123`
   - **What is wrong:** the mock level seed lacks `PENDENT` «Pendent» (S05 §12, B32, outside the progression). The published core has it: the D11 core capture shows Teràpia and Pendent both off. So the mocked D11 and D3 no longer match the seed.
   - **Related:** S05 §3 says `progression` also decides which levels appear in the D3 coverage table (R-06-06). The mock `/coverage` is still a static fixture.
   - **Suggested fix:** both are outside this task's Steps; a follow-up task could cover them.
9. **nit** `roadmap/evidence/E4-W06/D11-nivells-1280.png`
