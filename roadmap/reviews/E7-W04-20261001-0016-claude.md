# Review E7-W04 — minor issues

## Findings
1. **minor** `apps/clubs-admin/src/messaging/NotificationPreferencesBlock.tsx:162-195`: two paths can still lose the latest D10 choice.
   - **Why it happens.** The code uses the order in which answers arrive as if it were the order in which the PUTs reached the api. Once the newest request has been answered, `settled` counts it as confirmed. A later event can undo that, but nothing takes the confirmation back.
   - **Path (a): the resend fails.** Step 3's scenario: seq1 `{PERSONAL:false}`, then seq2 `{true}` as keepalive. seq2 answers, so `settled = 2`. seq1 answers late, which triggers the resend seq3. If seq3 then fails with `status 0`, `settled` stays at 2, and the check `settled >= newest.seq` (2 ≥ 2) runs `clearOutbox`. The api may hold `false`, and the recovery entry is gone.
   - **Path (b): the older PUT fails late.** seq1 fails with `status 0` after seq2 has answered. The catch branch never resends, even though seq1 may have landed after seq2. The outbox is cleared anyway.
   - **Path (c): the older PUT lands last but answers first.** No resend happens.
   - **Rule broken.** Step 3 says: «the latest choice must win, whatever order the answers arrive in … keep the recovery entry until the latest change is confirmed» (R-11-04).
   - **Suggested fix.** If the newest body was sent while an older PUT was still pending, resend it once after every older PUT has settled, however they settled (answer or network failure). Clear the outbox only on a 2xx for that final send; don't let a late event leave `settled` counting an answer it has cancelled.
   - Screen 12's `preferences-saver.ts` copies this rule, so its failure branch has the same gap (E7-W02 scope; it only needs a note).
2. **minor** `apps/clubs-admin/src/census/NotificationPreferencesBlock.test.tsx`, step 4 test: the reconcile branch has no test.
   - Step 4 asks to «reconcile the writes still pending» on `pageshow(persisted)`.
   - In the test, the departure's keepalive PUT has already answered and the outbox is empty (the test asserts `toBeNull()`) before `pageshow`. So `restore()` → `readOutbox` → `change(kept)` never runs with data.
   - Only the reset of the `left` flag is covered.
   - Fix: add a case where the keepalive PUT is held across `pagehide(persisted)`/`pageshow(persisted)`. The kept patch should then be sent again as a normal save after the held PUT settles, and the outbox should clear only after that save is answered.
3. **minor** `apps/clubs-admin/src/messaging/AnnouncementsPage.test.tsx`, step 5 test: the detail-read half of step 5 is untested.
   - Step 5 covers «saves and … overlapping detail reads».
   - `freshest()` in the detail effect (`AnnouncementsPage.tsx:129`) has no test where a `GET /message-templates/{id}` answer, delayed past a newer save answer, arrives with the older version.
   - The report claims this («An older detail read shows the newer version already received»), but no test shows it.
4. **nit** `apps/clubs-admin/src/messaging/AnnouncementsPage.tsx:326`: an older save answer returns before the draft cleanup.
   - Scenario: save 1 carries E1 (v4 on the api), and its answer is delayed. The admin reopens the template and hits [Desactiva] (`keepEdits`), which gives v5. Save 1's answer then arrives.
   - Result: E1 stays marked «sense desar» even though it is saved. The next [DESA] applies E1 again over whatever v5 holds (another admin's text, if v5 came from a read).
   - Suggested fix: when the answer is older, leave the detail alone but still drop the draft if `current[saved.id] === options.savedEdits`.
5. **nit** `apps/clubs-admin/src/messaging/SendAnnouncementDialog.tsx:203-213`: after `IN_PROGRESS` the dialog only asks the admin to press [ENVIA] again (A1).
   - CONVENCIONS_API §7 / E79 says «el client conserva la clau i torna a provar més tard», and step 1 says «retry with the same key». That can be read as the client retrying on its own.
   - If the admin closes the dialog after the message, the page never says the announcement went out, although it will.
   - A1 is flagged in the report; the organizer should confirm that a manual retry meets E79.
