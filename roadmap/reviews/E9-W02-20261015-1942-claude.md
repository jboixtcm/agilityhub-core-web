# Review E9-W02 — minor issues

Round 2 covers all ten points from the organizer's verification. The adapter, the course-core heading function, the door optimistic locking, `force`, `finishBuildSession`, the marker fix, the tokens, the error mapper and the viewer snapshots are each in place and tested. I found no blocker. The items below are gaps next to the round-2 fixes, plus small inconsistencies.

## Findings

1. **minor** `packages/api-client/src/core-api-store.ts:683-691` — Build-session events still have no default. `subscribeBuildObstacleStatuses` throws `CORE_API_BUILD_EVENTS_NOT_CONFIGURED` unless the app injects `subscribeBuildEvents`.
   - **Why:** the organizer ruled on question (a): "the viewer polls `GET /build-sessions/{id}` until the api types it". Neither the adapter nor the report mentions polling, so every caller (E9-W03, mobile) must write its own transport or crash.
   - **Fix:** when no subscriber is injected, poll `listBuildObstacleStatuses` on an interval, emit only changed obstacles, and clear the interval in the returned cleanup. Add a fake-timer test. If the organizer prefers E9-W03 to own this, the report should say so.

2. **minor** `packages/api-client/src/core-api-store.ts:521-589, 700-718` — Marker writes still overwrite each other silently. `createMarker` and `updateMarker` go through `#putGeometry`, and `ringGeometryRequest` sends the version it has just re-read (`current.version`).
   - **Why:** if two editors change the same marker field, the last one wins without any `409`. The door path now sends the version the user edited (round-2 #3), but the same R-16-04 race on markers was not covered. Patching only the edited fields limits the damage to that field, but nothing detects the conflict.
   - **Fix:** take the version the caller read (optional `geometryVersion` on `UpdateMarkerPatch` / `CreateMarkerInput`), or compare `existing` with the marker snapshot the user edited and throw `STALE_VERSION` when they differ. Add an interleaving test like the door one.

3. **minor** `packages/api-client/src/core-api-store.payloads.test.ts:74,154,222,301`, `packages/course-ui/tests/*.tsx` — The round-2 tests are named `#N R-16-xx …`, not after spec test ids.
   - **Why:** AGENTS rule 5 asks for names after the spec ids (`T-xx-nn`). These are the front-side halves of S16 tests:
     - `force` → T-16-07
     - `finish` → T-16-10
     - geometry `STALE_VERSION` → T-16-06 / R-16-04
     - warning rule names in ca/es/en and the locale formatting → T-16-22
     - the snapshots and the interaction test do carry T-16-04, which is correct.
   - **Fix:** prefix the matching `T-16-nn` and keep the review number as a suffix.

4. **minor** `packages/i18n/src/locales/{ca,es,en}/enums.json:360` — The seven `courseWarningRule.*` labels are invented copy. There is no D18 mockup and S16 §2/§13 proposes no literals for them.
   - **Why:** the report flags them correctly, as AGENTS rule 1 requires, but nobody has approved them yet.
   - **Fix:** the organizer or Jordi approves or replaces them.
   - **Related:** `packages/i18n/src/course-texts.ts:5` redefines `CourseWarningRule` by hand instead of deriving it from course-core's `WarningRuleId`. A rule added to the engine would compile without a label. A type-level equality test, or deriving the list from course-core, would catch this drift.

5. **nit** `packages/api-client/src/core-api-store.ts:283,406` — `#courseUploads` is never pruned.
   - Every upload key keeps its full `normalizedJson` for the life of the store.
   - A replay also ignores any change to `input.courseData` sent under the same key.
   - **Fix:** delete the entry once the api has answered with a 2xx or a 4xx that retires the key.

6. **nit** `packages/course-ui/src/components/ui/Button.tsx:18` — The `danger` variant uses `bg-danger text-primary-fg`.
   - In the light theme that is white on `#e05b5b`, about 3.6:1, below AA for normal text.
   - With a club whose primary is light, `primary-fg` turns dark on red.
   - The dedicated `--ah-color-on-danger` token already exists (`tokens.css:45`). `tokens.test.ts` checks only the primary pair and the badge.
   - Nothing in course-ui uses the variant today. Use `on-danger` and add it to the contrast test, or drop the variant.

7. **nit** `packages/course-ui/src/components/RingDoorEditor.tsx:446-480` — After a `409 STALE_VERSION`, **[Save]** stays enabled.
   - Saving again repeats the same `409`.
   - [Revert] throws away the user's drafts without saying so.
   - This is acceptable under the "send the version the user edited" option. Still, disable Save while the error is `STALE_VERSION`, or tell the user that [Revert] loads the other editor's doors and discards theirs.

8. **nit** `packages/course-ui/e2e/harness.spec.ts:10-14,104` — The harness spec writes its PNGs to `roadmap/evidence/E9-W02` on every `pnpm e2e` run unless `E2E_CAPTURE_TASK` is set.
   - Any later local run overwrites the committed evidence for this task.
   - The test title says "moves the 2D and 3D views", but it only checks the 2D icon transform and the warnings count.
   - **Fix:** assert the 3D scene changed too (e.g. a group position read through a test hook), or rename the test.

9. **nit** `roadmap/evidence/E9-W02/r2-course-ui-harness-1280-dark.png` — Three things in the dark screenshot:
   - Warning messages are course-core's English `message`, e.g. «Course uses 1 × LongJump but ring "Pista central" has none on hand». The report says this is E9-W03 copy; make sure the organizer has it as a carried-over item, because course-ui passes `warning.message` through unchanged.
   - The `RingMarkerDiagram` (bottom centre) is almost empty in dark: the axis and ring-side labels are barely visible.
