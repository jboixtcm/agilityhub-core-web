# Review E9-W04: minor issues

## Findings
1. **major** `apps/clubs/src/courses/SetupViewerPage.tsx:291-320` (with `MemberRingSetup.courseId`): a MEMBER cannot see the plan of a setup that has only a placement. That is the setup every build-session `finish` registers, so it is the common case. The real-core screenshot `core-visor-alumne-375.png` shows «Jumping · muntat avui / No hi ha cap plànol per mostrar». Step 1 and R-16-16 ("`GET /courses/{id}` of a course referenced by a visible setup") are therefore only met for setups registered from the library or from a photo. The executor documents this correctly as an api proposal (Question 1), but `roadmap/MESSAGES.md` has no entry and no follow-up task is named. **Fix:** the organizer opens an api follow-up (the MEMBER projection carries the placement's `courseId`, or `resolvedObstacles`) and records this as a known gap at verification.
2. **major** `SetupViewerPage.tsx:400-418`, `RegisterSetupPage.tsx:176-184`, `courses/blocks.tsx:144-151`: the mobile build session can only start from the viewer of an ACTIVE setup that already has a `placementId`. Three things combine:
   - «Registra què hi ha muntat» never sends `placementId` (only `courseId` or a photo).
   - 07's «Recorregut previst» is plain text, not an action.
   - The «Sense recorregut registrat» state has neither [Sessió de muntatge] nor the join-by-code form.
   
   As a result, a planned placement (`ClassSession.placementId`) cannot be built from the phone until someone first registers it as built on the desktop (E9-W03's «Registra-ho com a muntat»). Nothing in `apps/` other than this viewer calls `createBuildSession`. S16 §2 places the button in the viewer, so this is literally compliant. Still, WP-16-F′ («sessió de muntatge mòbil, reutilitza `/live`») and T-16-16 imply you can build a course that is not set up yet. **Fix:** for staff, make 07's «Recorregut previst» start a session (`POST /build-sessions {placementId}`), and show the join form also on a ring with no setup. Or the organizer rules it out of scope and records it.
3. **minor** `apps/clubs/src/courses/shared.ts:121-140` vs `SetupViewerPage.tsx:107-151`: the code knows `GET /me/ring-setups` answers 403 to an ADMIN session without the INSTRUCTOR role. It falls back to `GET /rings/{id}/setups` only in `readActiveSetup` (the register form). `/recorreguts/muntat/:ringId` (`useMeRingSetup`) has no fallback, so an ADMIN-only user who opens it gets the generic «error + Torna-ho a provar». The register screen's close button falls back to that same route. The same 403 silently hides D12's strip for such an ADMIN (`AgendaRingSetups.tsx:58-65`). **Fix:** reuse the `/rings/{id}/setups` fallback in the viewer (and in D12), or state that ADMIN-only sessions are out of scope.
4. **minor** `RegisterSetupPage.tsx:640-662`: S16 §2 says «Fins quan?» defaults to `builtAt + courses.setupAutoExpireDays`. The field stays empty with a help text and the api applies the default. The member never sees the actual date before registering. Acceptable if the parameter is not readable by the app, but it is not listed under Assumptions.
5. **minor** `RegisterSetupPage.tsx:197-201`: the upload grant sends `contentType: file.type`. Some camera and gallery files report an empty `type` (e.g. HEIC on some Android builds), so the api would refuse the grant with a generic form error instead of the photo-field error. **Fix:** check for an empty or non-`image/*` type before asking for the grant and show `photoRequired` or a type message on the photo field.
6. **minor** `SetupViewerPage.tsx` (header card): S16 §2 asks for «muntat … per {instructor}» (author shown to staff) and for the viewer to show numbering. The author is missing; this is documented as Question 2 (no `builtByName` in the contract), so it is fine. The organizer should carry it with Question 1.
7. **nit** `apps/clubs/src/courses/courses.test.tsx:171-185`: `taps < 5` counts the test's own `fireEvent` calls, so it can never fail. What actually proves T-16-16's «< 5 tocs» is that the flow completes after exactly those three interactions. That holds, but the counter adds nothing. **Fix:** drop the counter, or assert that no other control has to be touched (e.g. REGISTRA is enabled after kind + photo).
8. **nit** `BuildSessionPage.tsx:286-302`: `finish` calls `setError`/`setSession` without the `mounted.current` guard that `tap` uses. If the user leaves mid-request it is a harmless state update after unmount, but it is inconsistent.
9. **nit** S16 §2 vs the contract: the spec table says `409 BUILD_SESSION_FINISHED`, while the snapshot (and the mock) use 422. The code follows the contract, which is correct. The spec wording should be fixed by the organizer (adds to the executor's Question 4).
