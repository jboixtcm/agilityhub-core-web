## Findings
1. **minor** `e2e/core/e3-signup.spec.ts:402`: the date check can't catch a broken input. The e2e types `01/10/2026` and checks that the request sends `2026-10-01`. But `d2-signup-view-core.json` shows the core already proposes `proposals.nextInvoiceDate: "2026-10-01"`, and `load()` pre-fills the field with it. So the check would still pass if the input's `onChange` did nothing. Point 1 asked for proof that the admin fills the date and it gets sent. · Fix: type a different valid date (e.g. `01/11/2026` → `2026-11-01`).

2. **minor** `apps/clubs-admin/src/dashboard/SignupReviewPage.tsx:400`: a success message shows as an error. «Les dades s'han actualitzat.» (after EDITA LES DADES) uses the same `message` state as the errors, which always renders `<Toast tone="danger">`. You can see the red-bordered toast at the top of the re-shot `D2-signup-core-1280.png`, which the gate evidence relies on. This bug predates round 2. · Fix: store a tone with the message and use `success` for `signupReview.saved`. Then re-shoot D2 (or take the screenshot before the edit).

3. **minor** `SignupReviewPage.tsx:414,471`: D2 may crash on `null` fields. The report says core image `9e3a9c6` sends `null` for missing optional fields (`d2-signup-view-core.json` shows `paymentMethod.channel: null`, `maskedAccount: null`, `plan: null`). Round 2 made D11 handle this, but D2 still checks `payment === undefined` and `signup.upfront !== undefined`. If the core ever sends `paymentMethod: null` or `upfront: null` (e.g. an add-dog signup without an upfront payment), `payment.maskedAccount` / `signup.upfront.totalPaid` throws a TypeError. The same applies to `"familyGroupId" in holderResult.data`: a `null` would be sent as `familyGroupId: null`. None of today's scenarios hit this. · Fix: use `== null` checks on these nullable-in-practice fields, at least until the api answers the NON_NULL question in MESSAGES.md.

4. **minor** `packages/i18n/src/locales/{ca,es,en}/admin-census.json` (`signupReview.pending`): not an ICU plural. «pendent des de fa {count} dies» gives «fa 0 dies», visible in the D2 screenshot, and «fa 1 dies» for one day. CONVENCIONS_I18N asks for ICU plurals, and step 4b required the same fix on D1. This predates round 2. · Fix: `{count, plural, =0 {…avui} one {fa # dia} other {fa # dies}}` in all three locales.

5. **nit**: the masked-IBAN claim isn't backed by a capture. The report says the core returns `···· ···· ···· ···· 1332`, but `d2-signup-view-core.json` was captured before the IBAN edit, so it shows only `null`. The OpenAPI schema is just `type: string`. The compacted text in the screenshot is the only proof. · Fix: capture `paymentMethod.maskedAccount` again after the edit, so the api proposal has hard evidence.

6. **nit**: a failed run's log is missing. The report says the first `turbo` run of round 2 failed on a `Branding` typing, and its log was overwritten. The evidence rule wants one line plus a log file for each failed attempt, and this attempt has only the line.

7. **nit**: the date field is left without an accessible label for the other dogs. It renders only in the first dog card (`index === 0`). That's a reasonable call (the date belongs to the member), but in a multi-dog signup the field's error text sits in the first card only. Consider moving the field to the «Modalitat i tarifa» decision card, which is also where the plan is chosen.
