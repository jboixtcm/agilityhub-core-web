# Review E7-W01 — needs changes

## Findings

1. **major** `apps/clubs-admin/src/messaging/NotificationLogPage.tsx:285` — Default exports send `category` and `audience` as columns, but `/notifications/export` permits only `createdAt,code,recipient,channels,readAt`. The backend rejects the request with `INVALID_FILTER`. MSW incorrectly validates against projection fields, masking this failure. Violates Step 7 and AGENTS rule 4. Use a separate export-column mapping aligned with `x-columns`, tighten MSW validation, and test default PDF/XLSX exports.

2. **major** `apps/clubs-admin/src/messaging/SendAnnouncementDialog.tsx:99` — Confirmation survives switching template A → B → A because `confirmedFor` retains A’s key. A fresh dry run can return a different recipient count while the checkbox remains confirmed and sending becomes enabled. A read-only component probe reproduced this with three different counts. Violates Step 6 / R-11-13’s strong confirmation requirement. Invalidate confirmation on every selection change and bind it to the latest completed dry run; add the A → B → A regression.

3. **major** `apps/clubs-admin/src/messaging/AnnouncementsPage.tsx:304` — A save response updates the displayed detail unconditionally. Save A, select B while the PUT is pending, then let A finish: the selected template remains B, but detail becomes A, leaving the editor permanently showing its skeleton. A component probe reproduced this. Revisiting A and editing before its earlier save finishes can also lose the newer draft through unconditional removal. Violates Step 3’s editor behavior. Associate responses and draft cleanup with template/request generations, or prevent navigation during mutations; test delayed responses.

4. **major** `apps/clubs-admin/src/census/CensusRecordPage.tsx:749` — The entire D10 preferences block, including “Avisos enviats”, disappears against the adopted API implementation. The guard requires `emailByCategory`, `reminderOptionsMinutes` and `modules`; the adopted backend’s `CensusQuery.preferences()` projects only `categories`, `channels`, `reminderMinutesBefore` and `pushClubNews`. The overview schema is free-form, so the richer MSW fixture passes contract validation without exposing this mismatch. Step 8 / R-11-04 remains an integration gap. Coordinate a typed preferences read contract and adopt it; expose unavailable/error state instead of silently omitting the feature.

5. **major** `apps/clubs-admin/src/messaging/NotificationPreferencesBlock.tsx:129` — Calling an ordinary asynchronous PUT from `pagehide` does not ensure pending preferences survive full-page navigation. There is no `keepalive`; additionally, when another request is in flight, `flush()` leaves the next patch queued for a later timer. Only the block’s own log link awaits completion. The report’s full-page-save claim is supported by dispatching `pagehide` in jsdom, where the document remains alive. Violates Step 8’s persistence requirement. Await queued writes before navigation or implement an unload-safe persistence mechanism, and verify actual navigation plus reload in Playwright.

6. **minor** `apps/clubs-admin/src/census/CensusListPage.tsx:431` — D15 resolves selected dogs’ owners through one request capped at 1,000 rows. Selection persists across pages, so larger selections silently omit remaining owners while the dialog still reports the full selected-dog count. Violates Step 6 / R-11-13. Paginate or batch owner resolution, verify every selected dog was resolved, and test a selection exceeding the page limit.

7. **minor** `apps/clubs-admin/src/messaging/NotificationLogPage.tsx:78` — `filterValue()` turns array-valued applied filters into an empty string. Contract-valid `in`, `nin` and `between` filters therefore show blank values in the active-filter chips, obscuring which recipients or dates are selected. Violates Step 7 / `CONVENCIONS_API.md` §4. Handle arrays explicitly and test API-shaped multi-value and range filters.
