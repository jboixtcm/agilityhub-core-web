# Review E5-W03 — needs changes

1. **major** `apps/clubs-admin/src/catalogs/JobsCard.tsx:96` — Run history always requests page 0 with 20 items and discards pagination metadata. The drawer has no filters for `status`, `scheduledFor`, `trigger` or `dryRun`, making older executions inaccessible. Task step 4 explicitly requires a universal list. Implement filtering and pagination; test retrieving an older matching run.

2. **major** `apps/clubs-admin/src/planning/ClassRegistrantsPanel.tsx:147` — Registrants render `state` instead of the required API-derived `displayState`; the mobile implementation does likewise. An `ACTIVE` booking remains labelled “confirmada” after the class, including a no-show. This contradicts task step 1, its fixed conventions and S08 §6. Resolve the missing contract field upstream, render it without client-side derivation, and cover past bookings and “no presentat”.

3. **major** `apps/clubs-admin/src/training/TrainingRegisterPage.tsx:451` — Filter choices and counts use only the first 1,000 records, ignoring subsequent pages. The blocks implementation at line 735 has the same limitation. Values occurring only on later pages cannot be selected; this affects filter functionality, not just approximate counts. Task step 2 and `CONVENCIONS_API.md` §4 require complete filter values. Use the appropriate endpoint or exhaust pagination with stable ordering; test more than 1,000 records.

4. **major** `apps/clubs-admin/src/census/MemberBookingsCard.tsx:110` — “Veure'ls tots” increases page size to 1,000, then permanently hides the button even when further pages exist. Older bookings become inaccessible, and the action never opens the member-filtered list required by step 3. Provide that paginated list and link; test a member whose history exceeds the page limit.

5. **major** `apps/clubs-admin/e2e/e5-backoffice.spec.ts:227` — `T-15-33` explicitly accepts D4 dropping the selected class because risk-review fixtures reference nonexistent calendar classes. It asserts only the calendar heading and week, despite being named “opens D4 on the class”. The required flow remains broken against MSW, contrary to steps 5/9 and the Definition of Done. Align the fixtures and assert that the clicked class is actually selected, including a cancelled class.

6. **minor** `roadmap/tasks/E5-W03.md:314` — The report documents missing waiting-member names, registrant level chips, training end times/member numbers, and D10 class descriptions/rings. These are explicit step 1–3 deliverables, so “Steps 0–9 done” at line 59 overstates completion. Obtain the upstream contract additions and implement them, or obtain an explicit organizer deferral and report these steps as partial. Do not hand-edit the verified snapshot.

7. **minor** `packages/api-client/src/mocks/backoffice-handlers.ts:477` — The new waitlist-cancellation mock permits any impersonation scenario to bypass the ADMIN check, without verifying ownership, and always records `cancelReason = ADMIN`. It also omits the WAITLIST module check. This mock cannot validate the authorization requirements in S08 R-08-16/R-08-19 and task step 6. Enforce the applicable role, ownership and module rules; add denial tests. This finding concerns the mock, not a demonstrated production vulnerability.

8. **minor** `apps/clubs-admin/src/training/TrainingRegisterPage.tsx:550` — Historical blocks resolve their ring through `useActiveRings`, which explicitly removes inactive rings. Consequently, a block belonging to a deactivated ring displays its UUID instead of its name and color at line 628. Step 2 requires readable ring information in the register. Resolve against all relevant rings and test an inactive ring with historical blocks.

9. **minor** `apps/clubs-admin/src/training/TrainingRegisterPage.tsx:406` — The date filter exposes the universal component’s `between` and `exists` operators, but supplies only individual date values. Selecting `between` therefore serializes a single-ended range; `exists` receives a date instead of a boolean. This violates the filter contract in `CONVENCIONS_API.md` §4. Supply operator-appropriate controls or restrict available operators, and test the resulting query strings.
