2. **major** `packages/api-client/src/mocks/fixtures/bookings.ts:849` (`limitReachedDetails`) with the fixed `WEEKLY_LIMIT_DONE` row (`booking-handlers.ts:190`): item 6 swapped phantom ids for a refusal the api can never send.
   - **What the mock answers now:** `409 BOOKING_LIMIT_REACHED {current: 1, limit: 2, notSelectable: [], swappable: []}`.
   - **What the api does:** S08 R-08-09 and the §6 pseudo-code throw it only when `limit.reached && limit.swappable.isEmpty`. Here the limit is not reached, and Duna's Monday 3 booking is ACTIVE and more than 4 h away, so it is swappable. This breaks the fixed convention «Mocks behave like the api».
   - **Visible result:** `29-limit-375.png` now reads «Aquesta setmana ja has fet **una** classe amb la Duna». That is false at the clock (Sunday 2, 20:30): Monday's class has not happened yet. It also departs from mockup 29 («dues») and the S08 §2 row-29 example (AGENTS rule 1, mockup fidelity).
   - **The tests don't catch it:** two of the three item-6 tests are vacuous.
     - `booking-handlers.test.ts:600` «no notSelectable id is a phantom» and `:631` «no class of a NEXT week is DONE» both run `every`/`filter` over a `notSelectable` that is `[]` in the `member` world.
     - That is the same weakness nit #12 called out.
   - **Disclosure:** the executor reported this openly as R2-A1, with the right alternative.
   - **Fix:** a dedicated scenario for the 29-limit capture, in which Duna's current week really holds two non-swappable bookings (for example the Sunday 20:00 class that has already begun plus a `CANCELLED_LATE` one). In that scenario the refusal is real (`current = limit = 2`, `notSelectable` non-empty, `swappable` empty). Make the `WEEKLY_LIMIT_DONE` row refuse only when `limitStatus(...).reached && swappable.length === 0`, otherwise return the normal hold. Assert `notSelectable.length > 0` before any `every`.
