# Review E4-W13 — needs changes

## Findings

1. **major** `packages/api-client/src/mocks/fixtures/signup-review.ts:566` and `apps/clubs-admin/src/dashboard/SignupEditDrawer.tsx:520`/`:564`: withdrawing a submitted type that the reused dog's record also has doesn't work the way the api does.
   - **The mock is wrong.** When a type is sent with `files: []`, the mock drops that type from the view.
   - **What the api does.** The api's view shows "the documents the validation will write" (`SignupService.documentRows`/`replaced`: the dog's own rows, with each submitted type replaced). So after a withdrawal it shows the record's own document again. `changedFields.documents` only compares the types sent with files (`dogReadmissionView`, `withFiles`).
   - **Example (T-04-12's case).** Kiwi's record has `cartilla_Kivi_2025.pdf` and the applicant sent a new card. Removing both new card files gives:
     - in the mock: no card, and «Abans: cartilla_Kivi_2025.pdf / Ara: …» with the card missing;
     - in the core: the old card is back, and «documents» is not a change.
   - **The drawer has a dead control.** It then lists the record's own file with [Retira]. Clicking it sends `{type, files: []}`, which the api treats as a no-op (E5-T21: `saveDocuments` returns false). The file stays, and no message is shown.
   - **Why it matters.** It breaks Step 5 ("mocks behave like the api"), R-04-06 ("un tipus … enviat sense fitxers conserva el del gos") and R-04-19.
   - **Why the tests miss it.** The Vitest and the mock e2e only withdraw `INSURANCE`, which the record doesn't have. The real-core run can't show it either, because Brisa E3's card has no files (finding 3).
   - **Fix:**
     - In the mock, a withdrawn type falls back to `readmission.current.documents`' row for that type. `dogReadmissionChanges` compares only the types sent with files, as the api does. Also mirror E5-T21: a PATCH that changes no key writes nothing and doesn't bump the version.
     - In the drawer, offer no [Retira] when the file is the last one of a type whose shown row is the record's own (not submitted), or explain why.
     - Add a Vitest that withdraws `VACCINATION_CARD` for Kiwi.

2. **minor** `e2e/core/e3-signup.spec.ts:1364`: the real-core "add a file" step passes on either outcome.
   - It accepts `200` or `400 FILE_NOT_FOUND`. The recorded run took the 400 branch (`d2-readmission-add-file-core.json`).
   - Since then, R-04-19 was amended (26-09) and api E5-T24 accepts the admin's `DOG_DOCUMENT` upload. From now on, the fallback branch turns an add regression into a green test.
   - The drawer's add path (upload, then kept keys plus new key) is therefore proven only in Vitest/MSW, never on the core.
   - **Fix:** once the core image carries E5-T24, make the 200 branch mandatory and drop the 400 fallback. Meanwhile, say in the report that step 2's add is unverified on the core.

3. **minor** `e2e/core/e3-signup.spec.ts:794`, `:1468`: the rejection check (step 6, T-04-19, R-04-23) is close to vacuous for documents and breed.
   - The reused dog, Brisa E3, was created with no card file (`attachCard` defaults to false). `readmission-core.json` shows `"VACCINATION_CARD: "` both before and after.
   - The readmission doesn't change the breed either (Mestís in both).
   - So "la cartilla antiga (fitxers inclosos, encara referenciats)" and "la raça antiga" from T-04-19 are never exercised.
   - **Fix:** pass `attachCard: true` to Pau's first `completePublicSignup` (`:794`) and change the breed in the readmission. D2 should then show «Abans: cartilla_Brisa_E3_1.jpg». This would also exercise finding 1 on the core, because the withdrawal would bring back the old card.

4. **minor** `apps/clubs-admin/src/dashboard/SignupReviewPage.test.tsx:1334`: the describe carries `T-04-19` (R-04-23 rejection), but none of its 9 tests asserts anything about a rejection. AGENTS rule 5 requires the T-id to match what is asserted.
