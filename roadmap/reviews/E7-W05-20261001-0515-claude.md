## Findings
1. **minor** `packages/api-client/src/preferences-saver.ts:199-206`, `:171-176` (A2): after a back-forward cache restore, the page can show a stale value as saved, and the outbox can be emptied.
   - **Why:** the saver treats the answer with the highest sequence number as "what the api holds". Step 1's premise is that answer order says nothing about landing order. A2 also frees the outbox on an open page once nothing is unsaved, even after a failure.
   - **Scenario:**
     1. The member leaves while seq1 `{false}` is out; seq2 `{true}` goes with keepalive.
     2. The page comes back from the cache before either settles.
     3. seq1 lands after seq2. The page now treats seq2's answer as the api's state, so it shows `true`, but the api holds `false`.
     4. The resend seq3 fails.
     5. The adopted normal save seq4 also fails.
   - **Result:** the toast says the save failed, the switch shows `true`, the api holds `false`, and the outbox is empty. This goes against step 1's "the latest choice is saved or stays in the outbox", but it needs a restore plus two failures. It needs only one failure when `outbox.take()` returned nothing, for example with storage unavailable.
   - **Suggested fix:** after a failed `PUT` on a page whose departure had overlapping `PUT`s, re-read with `GET` (or keep the entry) instead of trusting `server`. At minimum, record this as a limit of A2.
2. **minor** `apps/clubs/src/booking/shared.ts:81-110` (A5): the step 6 nit (E7-W02 #3) was about 03's quiet refetch. `useLoader` now keeps the old rows after *every* quiet reload that fails.
   - **Affected reloads:** 04's waitlist join and failed hold (`BookPage.tsx:211,231`), the waitlist detail (`WaitlistDetailPage.tsx:88,105`) and the booking detail (`BookingDetailPage.tsx:191`).
   - **Example:** after a successful waitlist join, a failed reload now leaves the joined row on screen next to the success notice (R-08-04 says it leaves the list). A second tap then gets an api refusal. Before, the page showed its error screen with a retry.
   - None of these screens has a test for the new behaviour.
   - **Fix:** limit the "keep rows" branch to 03's `refresh` and `pageshow` reloads, or have the organizer accept A5 explicitly.
3. **minor** CONVENCIONS_API §7 (E80) vs step 4's scope (A6, Q1):
   - E80 is general: «El web mostra aquest `409` amb un text propi… no amb el de `DIFFERENT_REQUEST`».
   - Eight keyed writes still show `errors:IDEMPOTENCY_KEY_REUSED` on `IN_PROGRESS`, and the clubs-wide `errorText` (`booking/shared.ts`) has no `IN_PROGRESS` branch. These writes also drop their key, against E79's «el client conserva la clau».
   - The executor flagged this as Q1. The task wording ("wherever a write keeps its key") supports the narrow reading, but the organizer should open the proposed follow-up before E7-W03 closes, or accept the gap explicitly.
   - **nit:** Q1 is slightly inaccurate. D12's ring-block drawer uses `useCalendarErrorMessage` (`RingBlockDrawer.tsx:78`), so it now shows `common:inProgress`, although it makes a new key on every attempt (`:198`). In practice that path cannot be reached with a fresh key, but the Q1 list should not include D12's blocks.
4. **nit** `apps/clubs/src/profile/NoticesCard.tsx:85` and `apps/clubs-admin/src/messaging/NotificationPreferencesBlock.tsx:138`: `saver.restore(outbox.take())` runs `take()` before `restore()` checks `left` (`preferences-saver.ts:301`).
   - A restored page that left with nothing unsaved still takes over a newer visit's entry for the same scope, then ignores it.
   - If that page later leaves with changes of its own, its `write()` overwrites the newer visit's kept change.
   - **Fix:** adopt whatever `take()` returns even when `left` is false, or call `take()` only when the saver was left.
5. **nit** `apps/clubs/src/booking/HomePage.tsx:41-48` (A4): when a pending marker is honoured, 03 reads `/me/home` at once and again after the resend, so the bell shows «2 sense llegir» for a moment.
   - Step 3 says "sends read-all again, then reads `/me/home`". Holding back the first read, or the dot, while the marker is pending would avoid the flash.
   - The marker also survives every keepalive read-all whose answer was lost when the document went away. That is the normal 11 → «Inici» path, so 03's resend is the common case, not the exception. This widens A4's window; Q3, the api's upper bound for `read-all`, is the right fix.
6. **nit** `apps/clubs/src/SignupPage.test.tsx:1105-1106`: the two new rows share one title, «IDEMPOTENCY_KEY_REUSED (409) → undefined», because `$path` is undefined.
   - In log `09`, the failure text identifies the `IN_PROGRESS` row, but the test names do not say what each row asserts.
   - **Fix:** add the reason to the title, e.g. `$code ($status, $details.reason)`.
