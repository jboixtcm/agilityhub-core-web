# Review E6-W05: minor issues

## Findings

1. **minor** `packages/api-client/src/followup.ts:159,307`: held keys are not tied to the submission that holds them.
   - **What happens:** `held` is one hook-wide `Set<fileKey>`. `upload()` reuses a held key past its grant for any later submission, not only for "the retries of an unanswered submission" (step 1, E74).
   - **Scenario on the real api:** a `POST /tasks` creates T1 with K1, but its answer is lost. The user edits the text and presses «Afegeix». The new body S2 gets a new `Idempotency-Key` but still carries K1. `TaskService.create` → `AttachmentService.add` finds K1 bound to T1 and answers `422 ATTACHMENT_ENTITY_MISMATCH`.
   - **Why it stays stuck:** `withUploads` re-uploads only on `INVALID_STATE`. The next press reuses K1 again, because its grant is still live, so every press fails until the five minutes are over.
   - **Why no test catches it:** the MSW `POST /tasks` handler (`followup-handlers.ts` ~l.266) does not model a key already bound to another task. It would create a second attachment with the same fileKey, which the api does not do.
   - **Context:** the old code kept keys forever, which was a permanent dead end, so this is an improvement but not the step's rule.
   - **Suggested fix:**
     - Key `held` by submission signature, and reuse a held key only when the same signature is sent again.
     - Or drop and re-upload a reused key refused with `ATTACHMENT_ENTITY_MISMATCH` too.
     - Make MSW refuse a key bound to another entity, and add a test: lost-but-created creation → edited text → retry.

2. **minor** `packages/api-client/src/followup.ts:303` (and the report's A5b): step 2 only holds for ADMIN.
   - **What happens:** an INSTRUCTOR (the main role of 26 and D13) cannot read the limits, so the picker accepts everything. For a JPEG + EXE selection, `upload()` PUTs the JPEG, then fails at `upload-url` for the EXE (`FILE_TYPE_NOT_ALLOWED`). It throws before registering anything.
   - **Result for an instructor:** the JPEG is not attached. The block shows one code message without the refused file's name.
   - **Why it matters:** step 2's stated outcome ("the JPEG is attached and the executable's message stays") is only tested and true with `scenario: "admin"`.
   - **Suggested fix:** in `addAttachments`, upload and register each file on its own, and report each failure as `«<name>: <code message>»` (reuse `labels.rejection`). Or have the organizer explicitly accept A5b as the step's scope.

3. **nit** `apps/clubs-admin/src/followup/followup.test.tsx:~526`: step 5's last assertion does not prove what its name says.
   - The test name says "the api's count wins when it answers", but the api answers 5, the same as the restored local value. The assertion would pass even if the api's answer were ignored.
   - **Suggested fix:** mark another note read in the fixture while offline, so the api answers 4, and assert 4.

4. **nit** `apps/clubs-admin/src/followup/FollowUpPage.tsx:279`: after a successful retry, D14 reloads with its loading state (A8).
   - `readIds` already removes the highlight at once, so the `setReload` makes the whole table flash through loading, and possibly lose its scroll position, because of a toast action.
   - **Suggested fix:** refetch in the background, keeping the rows until the answer arrives. This is acceptable as is under step 6's "or".

6. **nit (information for Q1/A1, no change needed)**: the api source confirms A1.
   - `AttachmentService.claim` (api `AttachmentService.java:145`) throws `INVALID_STATE` with no details for an unbound grant past `expiresAt`.
   - A bound grant is exempt from that check, so the same fileKey replays. This matches the mock's replay for an already-registered key.
   - `TaskService.create` (l.54) goes through `add` → `claim`, so `POST /tasks` can answer `409 INVALID_STATE` even though its OpenAPI does not declare it. Q1 (declare it, ideally with its own `details.reason`) is justified and belongs to the api.
