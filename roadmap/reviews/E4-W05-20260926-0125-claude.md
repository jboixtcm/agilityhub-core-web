# Review E4-W05 — minor issues

## Findings

1. **minor** `apps/clubs-admin/src/activities/ActivitiesPage.tsx:72-80` (`activityFields`): the new `fields` projection only requests `title` when the «Activitat» column is visible.
   - **What breaks:** `labels.selectRow` (`ActivitiesPage.tsx:490`, `"Obre {title}"`) reads `item.title` on every row. It names the row checkbox and the chevron link's screen-reader text (`packages/ui/src/universal-list.tsx:898,939`). Hide the title column with `?fields=date` or a saved view, and the core returns `title: null` (the behaviour the executor reported). Every row link then reads «Obre null» or «Obre ».
   - **Why it matters:** AGENTS rule 6 (labels). The registrants page gets this right: it always asks for its row-label data (`member`).
   - **Fix:** always include `title` next to `id` in `activityFields`, and add a Vitest case with a view that has no title column.

2. **minor** `apps/clubs-admin/src/activities/ActivityRegistrantsPage.tsx`, `ActivitiesPage.tsx`, `packages/api-client/src/mocks/activity-handlers.ts:305-330`: this is a product and mock change outside the task's fixed conventions.
   - **Conventions it goes beyond:** "MSW/unit suites stay untouched except for the contract alignment of step 0". Step 3 also says "do not fix … unless one-line literal fixes".
   - **Why it is defensible:** the T-07-32 flow cannot pass on the real core without it (`400 INVALID_FILTER`). Tests that fail on the old code are provided (`01-`, `02-`, `03-vitest-*-before-fix.log`).
   - **Side effect:** the mock `fieldsProjection` now copies a core behaviour that contradicts the adopted snapshot. It answers `null` for required keys such as `registrationId: string` and `title`. This is the same thing the executor proposes the api change (Question 1).
   - **Fix:** the organizer should accept the scope change explicitly. If the api adopts proposal 1 (omit unrequested keys), the mock and the "always request the row key" logic need a follow-up. Link that follow-up to proposal 1 in MESSAGES.

3. **minor** evidence for the step 0 image checks. Two claims have no committed output:
   - **`demo-canic.yaml` in `/app/seeds`:** said to have been seen with a `docker compose run` probe. No output is pasted or logged.
   - **`--week-start` honoured:** the report cites the seed log line «218 changes (demo planning, week start 2026-09-21)». It is not in `10-`/`11-e2e-core-run*.log`, which only show the script's own `E4_WEEK_START=2026-09-21` echo.
   - **Why a green run doesn't prove it:** Spring Boot ignores unknown `--key=value` arguments. The week start passed is the current Monday, which is also the seed's natural anchor. So a seed that silently ignored `--week-start` would produce the same green run.
   - **Fix:** have `scripts/e2e-core.sh` save `docker compose logs seed` (the tail) into the evidence directory, and paste the probe output.

4. **minor** the gate evidence ran against an image older than the adopted contract (report Question 4).
   - **Gap:** image `1308743` predates snapshot `d791361`. T-06-28 and T-07-32 were proven against the pre-E5-T15 api. The E5-T15 changes are exercised only in MSW: `position` kept on a cancelled waitlisted registration, `instructorNames`/`ring`, `startTime`/`endTime`.
   - **Why it is only minor:** no consumer reads the new fields yet. The DoD ("S06/S07 contract is the real snapshot") is met on paper.
   - **Suggestion:** the organizer decides whether `e2e:core` is re-run once `:main` carries E5-T15 (it could piggy-back on E4-W11 step 6).

5. **nit** the gate line «Week generated from A/B + Saturdays and validated through the UI» is overstated.
   - **What actually happens:** the week generated in (a) is week +3. It stays DRAFT, and its Saturday class is later DELETED by the seminar. The week validated in (b) is week +1, which the seed generated. No single week is both generated and validated through the UI.
   - **Status:** this follows steps (a) and (b) as written, but the gate line should say it.
   - **Also:** (a) never checks that the Saturday template went into the generation. The `POST /weeks/{id}/generation` body is not checked for `saturdayTemplateId`. `classCount 38` matching the seeded draft week is only indirect evidence.
   - **Fix:** assert the request body.

6. **nit** `e2e/core/e4-core.spec.ts`: idempotence comes only from reseeding.
   - **Why:** the spec asserts seed state that it mutates:
     - `Places` `toHaveValue("12")`, then `"13"`;
     - `position: 3`;
     - `proposed === week +3`;
     - the «4/5 +2» class, which it then cancels;
     - «3 publicada / 1 esborrany».
   - **Consequence:** a second run on the same stack fails. The `runId` titles and the cleanup (f) are cosmetic.
   - **Status:** acceptable under "the stack is self-cleaning", but Assumption 4 should state plainly that the spec is not re-runnable on a used seed.

7. **nit** `e2e/core/e4-core.spec.ts`: some assertions are weaker than the step text.
   - **Torneig cells (d), line 717:** the five «Activitat · Torneig d'Estiu 2026» cells are counted over the whole week, not on the Saturday. `tournamentSaturday` is recorded but never used.
   - **Missing checks in (e):** «(no dog)» on the 03 row is not asserted.
   - **Missing checks in the es repeat:**
     - it never checks the admin list's «en lista de espera (n)» chip;
     - it never checks that the row disappears after the member's own cancellation (the member re-registers straight away).

8. **major (pre-existing, not introduced here)** `apps/clubs-admin/src/census/CensusListPage.tsx:59`: D5's default filter is `planId:eq:plan-member`, an MSW fixture id.
   - **Effect:** on the real core, a fresh `/abonats` lists nobody. The step 7 D5 captures only work because the spec clears the filters first (`e4-core.spec.ts:1082-1091`).
   - **Status:** the executor reported it (deviation 11). It is a production defect on a verified screen and needs its own task, not just a report line.
   - **Also needing tasks:** deviations 4, 6, 7, 9 and 10. Deviation 7 matters most: the D7 registrants table overflows at 1280 and clips the header and «Excel · PDF» (AGENTS rule 6).
