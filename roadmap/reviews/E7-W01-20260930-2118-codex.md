# Review E7-W01 — needs changes

## Findings

1. **major** `apps/clubs-admin/src/messaging/SendAnnouncementDialog.tsx:189` — A retry receiving `409 IDEMPOTENCY_KEY_REUSED` with `details.reason = IN_PROGRESS` deletes the submission’s key. After a network failure, this makes the next retry create another announcement while the original can still complete. Reproduced with the component: network failure → same-key retry → IN_PROGRESS → different-key retry. This breaks R-11-13 and `CONVENCIONS_API` §7. Preserve the key for IN_PROGRESS and test that the entire retry sequence produces one batch.

2. **major** `apps/clubs-admin/src/messaging/SendAnnouncementDialog.tsx:104` — The displayed count is matched only by template and recipients, not by the current dry-run request. Let A return 11, switch to B, then return to A before B answers: the old count reappears while A’s new dry run is pending. Checking its checkbox enables ENVIA; I reproduced a real-send call before either pending response arrived. This violates step 6 and round-2 item 2. Invalidate the count immediately and require both count and confirmation to belong to the latest request. Add a delayed-response regression test.

3. **major** `apps/clubs-admin/src/messaging/NotificationPreferencesBlock.tsx:235` — Leaving D10 sends a new combined PUT concurrently with the existing PUT. If PERSONAL=false is in flight, the admin changes it back to true and leaves, the keepalive PUT can save true first, clear the outbox, then the original PUT saves false last. Reproduced: the final value was false and the recovery entry was gone. This loses the latest choice despite step 8 / round-2 item 5. Preserve write ordering across navigation and retain recovery state until the latest change is confirmed after older writes. Test reversed completion order on the same preference.

4. **major** `apps/clubs-admin/src/messaging/NotificationPreferencesBlock.tsx:232` — `left.current` remains true after a page is restored from the browser’s back-forward cache. Subsequent departures skip both the keepalive save and outbox persistence. Simulating `pagehide(persisted)` → `pageshow(persisted)` → another change → immediate departure produced zero additional PUTs and no recovery entry. This leaves round-2 item 5 incomplete for browser navigation. Restore an active saving lifecycle on `pageshow`, reconcile outstanding writes, and test a second departure after restoration.

5. **minor** `apps/clubs-admin/src/messaging/AnnouncementsPage.tsx:315` — The late-save guard checks the template ID but not response freshness. Save A, reopen it while that response is delayed, then complete another save: the older response can replace the newer saved detail. Reproduced: the editor reverted from version 5 to version 4 with no draft remaining, while the server still held version 5. Round-2 item 3 requires request-aware handling. Reject older versions/responses, including overlapping detail reads, and test two completed saves whose responses arrive out of order.
