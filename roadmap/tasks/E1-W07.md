# E1-W07 · A1 — `packages/auth` cookie mode: refresh token in an HttpOnly cookie behind the same-site proxy (remove the WebCrypto storage)

## Objective
Jordi's decision A1 (06-09): the refresh token must not be readable from JavaScript. The api (E1-T13) now delivers it to browser clients (`clubs-app`, `clubs-admin`, `id-web`) as an `HttpOnly; Secure; SameSite=Strict; Path=/oauth2/token` cookie and accepts `grant_type=refresh_token` from that cookie; every app host is served through a same-site proxy (`/api/*` → core, `/oauth2/*` + `/.well-known/*` → id). Remove the WebCrypto-encrypted storage from `packages/auth`, keep only the access token in memory, and make the apps call same-origin relative URLs.

## Spec references
S01 v0.4 R-01-06 (cookie mechanics), §6 `/oauth2/token` (`tokenDelivery = COOKIE`) · `docs/DECISIONS_PENDENTS.md` A1, A11 · E1-W06 (identity vs core routing — now both are relative paths behind the proxy).

## Context to load
`packages/auth/src/{auth-client.ts, session.tsx, storage*.ts}` + tests · `apps/*/src/main.tsx` (client options) · `apps/*/vite.config.ts` (dev proxy) · `packages/api-client/src/mocks/handlers.ts` (token handlers) · `docs/playbooks/api-client-usage.md` · S01 R-01-06 · this file.

## Fixed conventions
- No refresh token ever touches `localStorage`/`sessionStorage`/IndexedDB: delete the WebCrypto storage module and its tests. Session bootstrap on load = `POST /oauth2/token` `grant_type=refresh_token` with `credentials: "include"` and **no** `refresh_token` field; a `400`/`401` means «no session» → screen 01 (never an error toast).
- Access token in memory only (module state / React context); the existing sliding refresh (before expiry, on focus, on 401) stays; concurrent refreshes are coalesced (one in flight).
- Base URLs default to **relative**: `apiBaseUrl = "/api/v1"`, `identityBaseUrl = ""` (so `/oauth2/token`, `/.well-known/…` resolve on the current host); the options remain overridable for tests/native contexts. `fetch` calls to `/oauth2/*` and `/api/*` use `credentials: "include"` (same-origin cookies).
- Dev proxy: each app's `vite.config.ts` proxies `/api` → `VITE_CORE_URL` (default `http://localhost:8080`) and `/oauth2`, `/.well-known`, `/connect` → `VITE_ID_URL` (default the same core in local), replicating the Caddy rules of `docs/DEPLOY.md`; document it in `docs/playbooks/api-client-usage.md`.
- MSW: token handlers set no cookie (MSW cannot); in mock mode the client keeps a **memory-only** refresh token behind the same interface so e2e flows still work — clearly marked as mock-only, never used in production builds (build-time guard).
- Handoff (`/entrar?handoff=`) and magic-link exchanges: same — the api sets the cookie on the target host; the client just calls the grant with `credentials: "include"` and drops any refresh token from the body if present.
- Logout: `POST /oauth2/revoke` with body `{}` and the bearer access token (COOKIE clients — the cookie's `Path=/oauth2/token` keeps it away from the revoke route; the server revokes the caller's session family and clears the cookie, api E1-T13) + clear memory; `apps/id` `/logout` unchanged otherwise.
- The api snapshot with these changes (`TokenResponse.refresh_token` optional, `RevokeRequest.token` optional, `Set-Cookie` documented, platform-roles routes) is staged at `packages/api-client/openapi/openapi.next.json`; this task may swap it into `openapi.json` **only if** `pending.json` does not redefine any of its paths (it should not: E2-W08 handles the census part) — otherwise leave the swap to E2-W08 and code against the documented shapes.
