### What changed, per step

1. **A failed handoff never falls back to the cookie (E47).**
   - `packages/auth/src/auth-client.ts` `performExchange`: when the token endpoint refuses an «Entra com l'abonat» code, answers 5xx, or cannot be reached (offline), the call now runs `endHandoff()` before rethrowing. That puts `{state:"ended"}` in session storage and sets `handoffEnded`.
   - `restoreSession()` then returns `null` without a `refresh_token` grant. After a reload it reads `ended` from storage and does the same.
   - `apps/clubs/src/App.tsx` (01, `failHandoff`):
     - a refused code shows «Aquest enllaç ja no és vàlid»;
     - a transient failure (`ApiError.status` 0 or ≥ 500) shows «No s'ha pogut completar l'accés. Torna-ho a provar.» with «Torna-ho a provar». That button sends the **same code** again: it was never redeemed. A success leaves the `ended` state through `leaveImpersonation()`;
     - a redeemed code whose `/me` fails keeps E4-W16's `retryHandoff()`.
2. **The back office's handoff — option A**: the `pending` and `ended` states apply only to an impersonation handoff.
   - New `AuthClientOptions.handoffSessions: "account" | "impersonation"`. The default is `"impersonation"`, which is the member app's handoff.
   - clubs-admin passes `"account"` through the new `apps/clubs-admin/src/auth-options.ts`, which `main.tsx` and the tests both use.
   - In `"account"` mode the handoff's tokens are an ordinary sliding session kept in memory, never in `sessionStorage`. `confirmAccountHandoff()` asks `/me` again on a network error or a 5xx (2 s, 5 s, or at once when `online`). After that, `hasPendingHandoff()` is true and `retryHandoff()` asks again. A 4xx drops the tokens.
   - clubs-admin `AccessPage`:
     - reads the code once, into state, and removes `?handoff=` from the address before redeeming it;
     - on a transient failure (of the code or of its `/me`) shows a retry card (`auth:access.genericError` + `auth:activation.retry`, disabled while pending);
     - on a refusal keeps «Aquest accés al backoffice no és vàlid o ha caducat.»;
     - while the retry card is up, listens to `signedIn` and opens `/tauler`.
3. **The real-core stage without its fallbacks.** `e2e/core/e4w16-core.spec.ts` no longer has the «missing `launchUrl`» branch nor the «first `PUT /me/password` answers 401» branch. The stage now asserts `launchUrl` is non-empty and that the first PUT answers `200`, with a message naming api E5-T27. Only the RESET link's `purpose` still falls back, with its «pending real-core proof» annotation, because api E5-T29 has not shipped it (`recovery-link-core.json`: `"purpose": null`).
   - Also: `e2e/core/e4-core.spec.ts` `loginClubs` now waits for `/instructor/dia`. Since E6-W01 round 2 #7 (ruling E71) an instructor lands on 20, and the e5 stage's helper already waits there. The e4 stage had been failing on that since E6-W01; see run 11 below.
4. **Two small fixes.**
   - es `auth:activation.retry` = «Vuelve a intentarlo».
   - `apps/clubs/src/dog-tasks-contrast.test.ts` now computes the task text's ratio with the token that paints `.dog-task p`, read from `styles.css` (`paintToken` → `--ah-color-text-muted`), in both palettes.
5. **A load-independent start-up budget.**
   - `mock-worlds.budget.test.ts` («imports the mock modules afresh…») now uses `relativeCpuCost`: this process's CPU time (`process.cpuUsage()`, user + system) for the import against the CPU time of the reference work (×10), minimum of 5 rounds.
