## Steps
1. **#2 · The impersonated cancellation asks for a reason (R-07-09, R-07-10).** Under impersonation, the admin cancels with `cancelReason: ADMIN`, and the `reason` is required. `CancellationDeadline.check` answers 422 `VALIDATION_ERROR` on `reason` without it, and E4-W04 step 8 was wrong to say `{}` for every case.
   - For an impersonated session, the confirmation asks for «Motiu» (1–500 characters, required; propose the literals) and sends `{reason}`.
   - A member session keeps sending `{}`.
   - A 422 on `reason` shows on the field.
   - MSW answers like the api: an impersonated cancellation without a reason gets 422.
   - Check what `cancellableUntil` the api returns to an impersonation token (R-07-09: the admin may cancel until `startsAt`). If it is the member's deadline, say so under «Questions» (an api question). Never compute a deadline in the web.
2. **#3 · The rich text is read-only while saving (R-07-04).** A `contenteditable` does not follow the fieldset's `disabled`, so text typed while the `PATCH` is pending is lost when `applySaved()` resets the form. Make the editor read-only (with `aria-readonly`) while busy. Vitest with a deferred `PATCH`: typing is refused while it is pending, and nothing typed is lost.
3. **#5 · The cancellation deadline is live (R-07-09).** The detail page compares `cancellableUntil` with the time the page was loaded. Re-evaluate it when the deadline passes (one timer to the deadline), and check again before opening the confirmation. Vitest with fake timers: the page opens a minute before the deadline, and after it passes the button becomes the «posa't en contacte amb el club» text without a remount.
4. **#6 · The instructor's «Nivells» (R-07-14).** An INSTRUCTOR cannot read `/parameters/{key}`. The swallowed 403 currently becomes `levelsEnabled: true`. Use the same rule as D4 (R-06-15 in E4-W02): without access to the parameter, show «Nivells» only when the activity itself has levels. Vitest: a club with levels disabled, an INSTRUCTOR, and an activity without levels → no «Nivells».
5. **#7 · The whole day for an activity away from the club (R-07-05).** The time options always follow the club's opening hours, but R-07-05 limits only ring-block windows. With `atClub: false`, or with no linked rings, offer the whole day (00:00–23:59 in the usual steps). Vitest: an activity away from the club at 06:00 can be entered when the club opens at 07:00.
6. **#8 · The MEMBER guard of the app detail (AGENTS rule 3, S07 §6).** `/activitats/:id` in the clubs app checks the login and the module, but not the role. Only MEMBER and IMPERSONATED sessions may open it; anyone else gets the app's usual «no access» path. Vitest with an instructor-only session.
7. **#9 · `ADMIN_TEXT_REQUIRED` after an empty preview (R-07-06).** If the preview had no registrants and someone registers before the confirmation, the 422 leaves the simple modal stuck, and every retry sends no text. On that 422, fetch the preview again and show the notice field with the error. Vitest.
8. **#10 · The `memberId` filter of the registrants (S07 §6, E4-W04 step 6).** Add the member filter (localized labels; the values from the list's filter values, or a member search). It survives saved views and the export (E4-W07 forwards the filters). Vitest.

1. **#2 · The impersonated cancellation reason (R-07-09/10).**
   - `ActivityDetailPage` takes `impersonated`.
   - For an impersonated session, the cancel and leave-waitlist confirmation shows «Motiu»: a `Textarea`, `required`, `maxLength` 500, with the help line «Anul·les en nom de l'abonat: el motiu queda registrat.». [ANUL·LA LA INSCRIPCIÓ] stays disabled until the trimmed reason is non-empty, and the request sends `{reason}`.
   - A member session keeps sending `{}` and shows no field.
   - A `VALIDATION_ERROR` whose `details.fieldErrors[]` names `reason` keeps the confirmation open. The error shows on the field, with `aria-invalid` and `aria-describedby`: «Escriu el motiu de l'anul·lació (fins a 500 caràcters).». The error is mapped by code, and it is tested with both 422 and 400 (see Q1).
   - The route passes `impersonated` from `me.impersonation` (`MemberActivityRoute`, step 6).
   - **Mock:** an impersonated `POST /activity-registrations/{id}/cancellation` without a reason, or with a blank one, answers `422 VALIDATION_ERROR {fieldErrors: [{code: REQUIRED, field: reason}]}`. With a reason, it records `cancelReason: ADMIN, byRole: ADMIN`.
   - **`cancellableUntil` under impersonation:** see Q2. The web shows what the api sends and computes nothing.
2. **#3 · The rich text is read-only while saving (R-07-04).**
   - `RichTextEditor` (`packages/ui`) takes `busy`. While busy:
     - `contenteditable="false"` and `aria-readonly="true"`, with `aria-busy` on the wrapper;
     - the toolbar stays in place, but its buttons and the link panel are disabled;
     - paste and blur do nothing;
     - an `input` that still reaches the editor restores its value instead of emitting.
   - D7 passes `busy={pending !== undefined}`: save, publish, cancel, unpublish and upload.
   - A disabled-tool style uses tokens only.
3. **#5 · A live cancellation deadline (R-07-09).**
   - `useBeforeDeadline(deadline)` in `ActivityDetailPage` replaces `loadedAt`. It sets one `setTimeout` to the api's `cancellableUntil` (the registration's, else the activity's). The timer is clamped to 2³¹−1 ms and re-armed if it fires early, so the button becomes «Per anul·lar la inscripció, posa't en contacte amb el club» without a remount.
   - `recheck()` reads the clock again before opening the confirmation and again before sending. A device that slept past the deadline closes the confirmation instead of sending.
   - A confirmation still open when the timer fires closes, unless a request is pending.
   - A non-finite deadline (loading, or a malformed date) arms no timer.
4. **#6 · The instructor's «Nivells» (R-07-14).**
   - `loadActivitySettings` returns `levelsEnabled: null` when `/parameters/levels.enabled` answers 403.
   - D7 shows «Nivells» when `levelsEnabled ?? (the activity's own levelIds.length > 0)`. That is the D4 rule of R-06-15.
   - **Mock:** `GET /parameters/{key}` answers `403 FORBIDDEN` to an INSTRUCTOR session without ADMIN (MATRIU_PERMISOS). There is also a new `activitiesInstructorNoLevels` scenario (`levels.enabled=false` + instructor).
   - D4 and D3 already fall back on a failed read, and the full e2e is green.
5. **#7 · The whole day away from the club (R-07-05).**
   - When `atClub` is false, or no ring is linked, the time options are `00:00–23:59` in `classes.slotMinutes` steps (so 0:00…23:50).
   - With linked rings they still follow `club.openingHours`.
   - A value outside the list is kept, as before (`withValue`).
6. **#8 · The MEMBER guard (AGENTS rule 3, S07 §6).**
   - `/activitats/:id` renders `MemberActivityRoute`:
     - an impersonated session gets `RequireAuth`;
     - any other session gets `RequireRole roles={["MEMBER"]}`. That is the app's usual no-access path (the same as `/instructor/avui` for a member): nothing renders in the shell;
     - then `RequireModule("ACTIVITIES")`.
   - An instructor-only session never calls `/me/activities`.
7. **#9 · `ADMIN_TEXT_REQUIRED` after an empty preview (R-07-06).**
   - `CancelActivityModal` takes `onRefreshPreview`. On `ADMIN_TEXT_REQUIRED` from the simple confirm:
     - it awaits a fresh `GET …/cancellation-preview`;
     - it switches to the notice-text layout, with the error on «Text de l'avís» (`aria-describedby`). If the fresh preview still reads 0, it keeps the text field anyway (`textRequired`);
     - the retry sends `{reason: CLUB_MANUAL, adminText}` with a new `Idempotency-Key` (one per payload).
   - The textarea is disabled while pending.
   - `ActivityPage` updates the preview only while the modal is still open.
8. **#10 · The `memberId` filter (S07 §6).**
   - The registrants' filter menu has «Abonat» (`relation`, operators `eq`/`ne`).
   - There is no registrants filter-values endpoint, so the values come from the list itself. The page reads one `GET /activities/{id}/registrations?size=1000&sort=memberLastName,asc` and shows «{name} · {number} (count)». That read is cached per activity, and a late answer for another activity is ignored.
   - The chip shows the member's name, also after a reload: the lookup loads when a `memberId` filter is applied from the URL or from a saved view.
   - The filter lives in the URL and in the saved views, and the export forwards it (E4-W07).
   - `loadFilterValues` is now memoized. It was an inline function, so `UniversalList` reloaded the values on every render of the page and reset the picked value.
- **Also:** the R-07-03 D7 test now waits for the editor's content. This is the flake E3-W10 reported: the content is filled in a passive effect.
