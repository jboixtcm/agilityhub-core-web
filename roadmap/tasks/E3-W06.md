## Steps
0. **Harness.** `scripts/e2e-core.sh` runs the E3 stage only for the evidence folders `E3-W03`…`E3-W05` (the E3-W05 run set `^E3-W0[345]$`). Extend it to `E3-W06`…`E3-W09`, so this task and the next three run the E3 scenarios on a fresh seed.
1. **B1 · the identity document at submission (R-04-01).**
   - The defect: `POST /signup` spreads `draft.person` (`SignupPage.tsx:1359`). Its `idDocument.type` stays `"DNI"` and the passport is never sent. A NIE applicant gets `400 INVALID_ID_DOCUMENT`, and a passport-only applicant a 400.
   - The fix: build the body's `idDocument` with `identityDocument()` (`:376-389`), the builder the identity check already uses. One source for both requests.
   - Vitest, on the request body:
     - DNI;
     - NIE: `x1234567-l` → `{type: NIE, value: X1234567L}`;
     - passport only: `{type: PASSPORT, value}`.
   - Real-core e2e: a NIE applicant reaches «Sol·licitud enviada».
2. **M1 · stable retries (CONVENCIONS_API §7, R-04-26/27).** Today every tap sends a fresh `Idempotency-Key` (`:1331, 1343, 1369, 1382`). The draft is also deleted before the checkout, and `signupToken` lives only in a closure.
   - Use one key per payload:
     - generate it when the step-19 payload is first sent;
     - keep it in the draft;
     - reset it when any field of the payload changes.
   - Keep `memberId`, `signupToken` and the checkout state in the session draft until the flow ends: the success page, or a resolved checkout. Delete the draft only then.
   - `?cs=cancel` goes back to 19 with the data. Its retry reuses the signup already created (checkout only); it is not a new `POST /signup`.
   
   Vitest:
   - a lost 201 (a network error after the server committed) → the retry sends the same key and gets the same 201;
   - add-dog, the same: the member's own dog never answers `DOG_CHIP_ALREADY_REGISTERED`;
   - a cancelled checkout → 19 keeps the data.
3. **M2 · errors mapped to fields and steps (§2 «400 del back mapejat a camps», CATALEG_ERRORS).** Today step 16 maps only `details.fieldErrors`. Step 19 handles five codes, and everything else becomes «No s'ha pogut completar l'acció.» (`:451-463`, `:1389-1404`).
   - Map each code to the field and the step that owns it, navigate there, and focus the field:

     | Code | Goes to |
     |---|---|
     | `INVALID_ID_DOCUMENT`, `ID_DOCUMENT_AMBIGUOUS` | 16, document |
     | `INVALID_PHONE` | 16, phone |
     | `INVALID_IBAN` | 19, IBAN |
     | `PLAN_NOT_AVAILABLE` | 18, plan, after reloading the config |
     | `DOG_DOCUMENT_REQUIRED`, `FILE_NOT_FOUND` | 17, documents |
     | `DOG_CHIP_ALREADY_REGISTERED` | 17, chip |
     | `FAMILY_HOLDER_NOT_FOUND` | 18, family |
     | `CONSENT_VERSION_OUTDATED` | 19, consents (step 4) |
     | `MEMBER_ALREADY_EXISTS`, `SIGNUP_ALREADY_PENDING` | the inline message of 16 (R-04-05) |
     | `SIGNUP_CLOSED` | the closed screen |
     | `RATE_LIMITED` | its own message |
   - Normalise the `details.fieldErrors` paths (`emails[0]`, `person.idDocument.value`, …) to the form keys.
   - Any other code: `t('errors:'+code)`, with the generic text as the last fallback.
   - Local checks of the ES profile before sending: the postal code, the birth date (past, ≥ 1900), `birthMonth` ≤ the current month, and the IBAN mod-97.
   - MSW answers with the api's real shapes and statuses: rule 0 (422 vs 409), and a top-level `code` with empty `details` where the api does that.
   
   Vitest: one table test over the codes.
4. **M19 · the consent version (R-04-17; GDPR art. 7).**
   - The defect: the version sent at submission is the current config's `legal.legalTextsVersion` (`:1311`). Meanwhile the draft keeps `privacyAccepted` for 24 h.
   - The fix:
     - store the accepted version together with the acceptance;
     - when a config reload brings another version, clear the acceptance and ask again;
     - send the accepted version;
     - on `422 CONSENT_VERSION_OUTDATED`, go back to the consents with the new texts.
   
   Vitest: accept v1 → reload with v2 → the box is cleared, and submission is blocked until it is accepted again.
5. **The payment texts under the right method (M7, web half; T-04-32).**
   - The cash conditions (`texts.cashConditions`) appear only when the recurring method CASH is selected.
   - The day-of-month text (`texts.paymentDay`) does not appear under CARD (Codex F30).
   - The MANUAL instructions come from `paymentMethods[MANUAL].instructions`. Api E3-T08 fixes their content; the field already exists.
6. **The signup minors**, with a test wherever there is behaviour:
   - `planId` and `planIdRequested` are omitted when empty (a club without signup plans; Codex F3).
   - The honeypot is `aria-hidden` and out of the tab order.
   - Focus moves to the first error **after** it renders, and `aria-describedby` links each field to its message.
   - The async upload and the town lookup update the draft functionally, with no stale overwrite.
   - `offerLabel` shows only with `FAMILY_GROUP`.
   - The image-consent text comes from `texts.imageConsent` when the config has it, otherwise from `legal.imageConsentText`. Say which one the current snapshot has.
   - The account holder is prefilled with the group holder when the family group is FOUND (R-04-10).
   - The `notesToInstructors` field on 17 and the `holderTaxId` field on 19 (§2, §3).
   - The add-dog success page does not promise a welcome email.
   - «Laia F..» → «Laia F.».
   - The chip is validated per profile (ES: 15 digits; GENERIC: 8–15 alphanumerics) and normalised.
   - The IBAN leaves the session draft when the method changes away from SEPA.
   - GENERIC profile: an editable phone prefix, and the profile's first document type as the default. It is latent (no GENERIC club yet), so a unit test is enough.
7. **Re-shoot** 16, 17, 18, 19 (monthly), «enviada» and add-dog 19 at 375, with `pnpm e2e:core E3-W06`. Compare each screen with its mockup in the report, one line per screen. The payment card itself changes in E3-W08.

### Assumptions
1. **`PLAN_NOT_AVAILABLE` goes to 17, not 18.** The task table says «18, plan». The plan selector («Modalitat») lives on screen 17 (S04 §2 row 17, mockup 17), and add-dog has no 18. The spec wins; the config is reloaded first, as the task asks.
2. **The day text under CARD.** S04 §2 row 19 lists `signup.text.paymentDay` under «Targeta», but T-04-32 and the task (Codex F30) say mandate + day text only under «Domiciliació». I followed T-04-32 and the task. The §2 row should be aligned.
3. **Checkout attempts.** The checkout key is stable across retries of the same attempt (network errors). A `?cs=cancel` return resolves that attempt: the retry asks for a new session for the signup already created, with a new key. `cancelUrl` is now `/apuntat-hi/pagament?cs=cancel` (or `/gossos/nou/pagament?cs=cancel`); the old `/apuntat-hi/enviada?cs=cancel` still lands on 19. Stripe itself is E8-T04.
4. **Old drafts.** A saved draft without `consentVersion` (written by the previous build) loses its privacy and image acceptance: it cannot prove which texts were accepted.
5. **Consent version for the image box.** `imageUse.version` is the same accepted version. A new legal version clears both boxes.
6. **`MEMBER_ALREADY_EXISTS`** shows `errors:MEMBER_ALREADY_EXISTS` («Aquest abonat ja existeix.») inline on 16, and `SIGNUP_ALREADY_PENDING` shows the R-04-05 literal `signup:person.alreadyPending`. `SIGNUP_CLOSED` shows the closed screen with `closedText` (fallback `errors:SIGNUP_CLOSED`) and reloads the config.
7. **The image-consent text in the current snapshot:** `SignupTexts.imageConsent` and `SignupLegal.imageConsentText` are both present and required in `openapi.json`. The front uses `texts.imageConsent` when it is non-empty, otherwise `legal.imageConsentText`.
8. **Add-dog** gets its own success route `/gossos/nou/enviada` (inside the authenticated `/gossos/nou*` tree). The 19 footer in add-dog mode uses the same non-welcome text.
9. **The birth-date and birth-month checks** use the browser's local date. The club's time zone matters only around midnight.
