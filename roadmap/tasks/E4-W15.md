### Real-core spec: E4-W13's add-file flow on image `ed9a33f`
The first full run (`14`) timed out in E4-W13's readmission part of T-04-34. The earlier runs of that flow used image `e9a58c1`, where the add answered `400 FILE_NOT_FOUND`. With E5-T24 it answers **200**.
- **Root cause.** The assertion message `expect(stored?.ok(), \`…${await drawerText()}\`)` is evaluated eagerly. `drawerText()` called `locator.textContent()` without a limit (`actionTimeout` is 0). On success no alert is ever shown, so it waited until the test's 480 s ran out.
- **How it was found.** The file timestamps put the stall between `D2-readmission-core-1280.png` and `d2-readmission-add-file-core.json`. The recorded timings show the upload-url, PUT and PATCH all answered within 80 ms of the click.
- **Changes to `e3-signup.spec.ts`:**
  - `drawerText()` now reads with `{ timeout: 1_000 }`;
  - the stack no longer adds the admin's bearer to `/attachments/uploads/**`. This follows your 26-09 message for an image carrying E5-T24;
  - the three waits of the add have a 120 s limit, and their timings go to `d2-readmission-add-file-core.json`.
- **Result.** The 200 branch (never run on the core before) passes, including both removals.
- **Kept as they were:** E4-W13's `400` fallback branch (dead with this image), and the LEFT-member lookup (it does not pick «Demo Boira» on purpose).
- **Diagnostic runs** (`15`–`19`):
  - the first attempts removed the `unroute`, replaced the `signed.text()` body read, and ran a probe;
  - each time the stall moved to the next step, which is how the eager message was found;
  - those intermediate edits were reverted except the route removal.
