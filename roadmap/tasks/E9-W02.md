### Assumptions

- Per S16 §14.2/§14.5, the current club is the sole R1 `Venue`; it is injected into `CoreApiStore` because the snapshot publishes club rings but no venue-list endpoint.
- The recovered components are a package, not an application route. There is therefore no E9-W02 screen/mockup screenshot; the complete existing three-app Playwright suite is the browser regression evidence. E9-W03 mounts these components in D18/D16 routes.
- The source planner's Supabase-only admin/event/collaborator methods are outside the twelve-component package surface. The adapter exposes only S16 operations that the authoritative snapshot publishes.

### Questions / catalog proposals

- The authoritative `/build-sessions/{id}/events` operation is currently described as an untyped `text/event-stream` and says the implementation returns `NOT_IMPLEMENTED`; it publishes neither a discriminated event payload nor the browser authentication parameter. An overlay cannot safely redefine that existing operation. Proposal for the API catalog: publish `obstacle`, `finished` and heartbeat event schemas plus the exact auth transport. Until then the consuming app supplies `subscribeBuildEvents` (authorized transport + parser + cleanup), while `CoreApiStore` owns the stable `PlannerStore` callback.
- `GET /placements` publishes only `ringId`, `courseId` and `activityId`; it does not publish the legacy planner's scope/date/venue calendar joins. No unsupported query fields were invented. If D18 needs server-side date windows, add them to the S16 contract first.
