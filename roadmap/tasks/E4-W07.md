# E4-W07 · Exports download the file the api returns

## Objective
The independent review of E4-W04 round 2 (`roadmap/reviews/E4-W04-20260924-2049-codex.md`, #1 and #4) found that exports break against the real core. The organizer confirmed it in both repos:
- **The api** (`ListExportService`, `ExportPolicy`) answers:
  - `200` with the file (PDF or XLSX, with `Content-Type` and `Content-Disposition`) when the export has up to 5000 rows (`SYNC_MAX_ROWS`), which is nearly always for a club;
  - `202 {jobId, statusUrl}` above that;
  - 422 `EXPORT_TOO_LARGE` above 100 000 rows, and 422 `EXPORT_LIMIT` when the club already has two exports running (S14 R-14-12, T-14-16).
- **The web** calls `client.GET(…/export)` with openapi-fetch's default `parseAs: "json"`. A real `200` therefore throws `SyntaxError` on `%PDF-1.7` before any page code sees it, and the census code would also corrupt the bytes by building the file from a string.
- **The mocks** answer only `202`, which hid it.

The affected buttons are:
- the census lists (`CensusListPage.tsx:895-940`, plus the selected-rows link at `:1001`);
- the audit (`AuditPage.tsx`);
- D7 (`ActivitiesPage.tsx:503`);
- the registrants (`ActivityRegistrantsPage.tsx:270`), whose export also drops the list's `q` (review #4).

**Each fix comes with a test that fails before the fix.**

## Steps
1. **One helper**, in `packages/api-client`, for example `requestExport(client, path, query)`:
   - request with `parseAs: "blob"`;
   - `202`: parse the JSON body and return `{kind: "queued", jobId}`;
   - `200`: return `{kind: "file", blob, fileName}`. The file name comes from `Content-Disposition`, with the `{list}.{format}` fallback, and the blob keeps the response's `Content-Type`;
   - errors still arrive as `ApiError` from the middleware.
   
   Add a small `saveFile(blob, fileName)` next to it (object URL, hidden link, revoke).
2. **Every export button uses the helper:** census members and dogs (including the selected-rows export), the audit, D7 and the registrants.
   - A queued answer opens the exports drawer, as today.
   - `EXPORT_LIMIT` shows the drawer notice.
   - `EXPORT_TOO_LARGE` and any other code show `errors:{code}` next to the button.
   - The registrants export sends the list's `q`, `filter`, `sort` and `columns` (review #4).
3. **MSW answers like the api.** Up to 5000 rows: `200` with a small binary body (`%PDF-` for PDF, `PK\x03\x04` for XLSX), the matching `Content-Type`, and `Content-Disposition` with the api's file name. Above that: `202`. A scenario switch forces `202`, so both paths stay testable.
4. **Tests:**
   - per button, a Vitest for each answer: `200` saves a Blob with the right name and type, and `202` opens the drawer;
   - a unit test that the saved bytes are identical to the response bytes (binary-safe);
   - the registrants export carries `q`.
5. **Real core.** In `pnpm e2e:core`, download a members export from D5 against the real core (the Playwright `download` event), and check the file name and the magic bytes. The activity exports get the same check in E4-W05, with the E4 seed.

### Summary per step
1. **One helper**, `packages/api-client/src/exports.ts`, exported from `@agilityhub/api-client`:
   - `requestExport(client, path, query)`:
     - it calls `client.GET(path, { params: { query }, parseAs: "blob" })`, so the body is never parsed as JSON or text;
     - `202`: it parses the Blob as JSON and returns `{kind: "queued", jobId}`. A 202 without a job id is a `TypeError`, not a download;
     - `200`: it returns `{kind: "file", blob, fileName}`. The blob keeps the response's `Content-Type` (re-wrapped from `arrayBuffer()` only if the types differ). `fileName` comes from `contentDispositionFileName()`: `filename*` (RFC 5987) first, then the quoted or bare `filename`, path parts stripped, fallback `{list}.{format}` (e.g. `activity-registrations.pdf`);
     - errors stay the middleware's `ApiError`;
     - `ListExportPath` is derived from the generated `paths`: every `/…/export` whose GET query takes the list's parameters. `/instructor/week/export` is excluded, with a `@ts-expect-error` test.
   - `saveFile(blob, fileName)`: an object URL, a hidden `<a download>` appended to the page, clicked, then removed. The URL is revoked 40 s later, because some browsers still read it after `click()`.
2. **Every export button uses it**, through one hook, `apps/clubs-admin/src/audit/useListExport.ts`:
   - a queued answer opens the exports drawer (as before); `EXPORT_LIMIT` opens it with its notice;
   - `EXPORT_TOO_LARGE` and every other code show `errors:{code}` under the Excel/PDF buttons, inside the open export menu. A non-api failure shows the new `census:list.exportError` fallback;
   - one export at a time: a ref guard, and both formats disabled (`aria-busy` on the panel) until the answer arrives;
   - `UniversalList` (`packages/ui`) takes a required `onExport` plus `exportBusy` and `exportError`. `getExportHref` and its `<a download href="/api/v1/…">` links are removed: they could never send the bearer token;
   - the pages:
     - D5/D15, `CensusListPage.tsx`: the menu, and «Exportar selecció», now a `Button` with its error in the bulk bar;
     - the global and member audit, `AuditPage.tsx`: its page toast for export errors is removed;
     - D7, `ActivitiesPage.tsx`;
     - the registrants, `ActivityRegistrantsPage.tsx`. They now send the list's `q`, with `filter=activityId:eq:{id}` + the list's filters, `sort`, and the columns without `contact` (not an `activity-registrations` export column). This is review #4;
   - **«Exportar selecció» sends only `filter=id:in:{ids}`** (R-03-24), plus `sort` and the visible columns:
     - the selection of `UniversalList` survives a new search or filter, so ANDing `q` and the filters could silently drop selected rows;
     - my first draft kept the old ANDed behaviour, and the new test fails on it (`11`).
3. **MSW answers like the api.** New module `packages/api-client/src/mocks/list-exports.ts`, used by `handlers.ts`:
   - **up to `SYNC_MAX_ROWS` (5000):** `200` with a 20/21-byte binary body. The PDF body is `%PDF-1.7\n%âãÏÓ…%%EOF` and the XLSX body is `PK\x03\x04…` with `0xFF 0xFE 0x80` in it; neither is valid UTF-8. The response has the matching `Content-Type` and `Content-Disposition: attachment; filename="{club.slug}_{listKey}_{yyyyMMdd-HHmm}.{ext}"` in the club's zone (R-14-12). The real core sends exactly this header shape (Evidence 4);

The registrants list and export apply `q` over the member name, and the export also accepts `activityId`. It shows only for non-api failures (network, malformed 202) and for codes without an `errors:` entry.

6. **The object URL** is revoked 40 s after the click, not right away (FileSaver.js uses the same delay), so a slow download never finds it revoked.
