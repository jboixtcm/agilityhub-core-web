# E4-W07 · Exports download the file the api returns

## Objective
The independent review of E4-W04 round 2 (`roadmap/reviews/E4-W04-20260924-2049-codex.md`, #1 and #4) found that exports break against the real core. The organizer confirmed it in both repos:
- **The api** (`ListExportService`, `ExportPolicy`) answers:
  - `200` with the file (PDF or XLSX, with `Content-Type` and `Content-Disposition`) when the export has up to 5000 rows (`SYNC_MAX_ROWS`), which is nearly always for a club;
  - `202 {jobId, statusUrl}` above that;
  - 422 `EXPORT_TOO_LARGE` above 100 000 rows, and 422 `EXPORT_LIMIT` when the club already has two exports running (S14 R-14-12, T-14-16).
- **The web** calls `client.GET(…/export)` with openapi-fetch's default `parseAs: "json"`. A real `200` therefore throws `SyntaxError` on `%PDF-1.7` before any page code sees it, and the census code would also corrupt the bytes by building the file from a string.
- **The mocks** answer only `202`, which hid it.

The affected buttons are:
- the census lists (`CensusListPage.tsx:895-940`, plus the selected-rows link at `:1001`);
- the audit (`AuditPage.tsx`);
- D7 (`ActivitiesPage.tsx:503`);
- the registrants (`ActivityRegistrantsPage.tsx:270`), whose export also drops the list's `q` (review #4).

**Each fix comes with a test that fails before the fix.**

## Steps
1. **One helper**, in `packages/api-client`, for example `requestExport(client, path, query)`:
   - request with `parseAs: "blob"`;
   - `202`: parse the JSON body and return `{kind: "queued", jobId}`;
   - `200`: return `{kind: "file", blob, fileName}`. The file name comes from `Content-Disposition`, with the `{list}.{format}` fallback, and the blob keeps the response's `Content-Type`;
   - errors still arrive as `ApiError` from the middleware.
   
   Add a small `saveFile(blob, fileName)` next to it (object URL, hidden link, revoke).
2. **Every export button uses the helper:** census members and dogs (including the selected-rows export), the audit, D7 and the registrants.
   - A queued answer opens the exports drawer, as today.
   - `EXPORT_LIMIT` shows the drawer notice.
   - `EXPORT_TOO_LARGE` and any other code show `errors:{code}` next to the button.
   - The registrants export sends the list's `q`, `filter`, `sort` and `columns` (review #4).
3. **MSW answers like the api.** Up to 5000 rows: `200` with a small binary body (`%PDF-` for PDF, `PK\x03\x04` for XLSX), the matching `Content-Type`, and `Content-Disposition` with the api's file name. Above that: `202`. A scenario switch forces `202`, so both paths stay testable.
4. **Tests:**
   - per button, a Vitest for each answer: `200` saves a Blob with the right name and type, and `202` opens the drawer;
   - a unit test that the saved bytes are identical to the response bytes (binary-safe);
   - the registrants export carries `q`.
5. **Real core.** In `pnpm e2e:core`, download a members export from D5 against the real core (the Playwright `download` event), and check the file name and the magic bytes. The activity exports get the same check in E4-W05, with the E4 seed.
