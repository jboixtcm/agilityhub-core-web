### Step 2 · the diagnosis (T-04-34, INC-07, INC-36)
**The session was never lost.** The add-dog success page (`/gossos/nou/enviada`, a full page load) never rendered, so it never asked for a token. Its boot was waiting for a `GET /api/v1/branding` that never answered.

**Instrumentation** (`e2e/core/oauth-token-log.ts`, `e2e/core/e3-signup.spec.ts`). It logs no value, ever:
- Each token call now names its browser context (`w<worker>c<n>`) and its page. It also records when it left, any other token call of the same context still out (`overlap`), and the `Set-Cookie` attributes of its answer.
- Each full page load is logged with the names, paths and expiry of the cookies in the jar.
- On a failure, the e3 spec writes `enviada-add-dog-failure-core.json`: every call since [ENVIA] (method, path, status), the requests still unfinished, the storage key names, console errors (query values stripped), page errors, and two 5 s probes of `/api/v1/branding` (from the page and from the runner through the dev proxy).
- Every run also writes `enviada-add-dog-boot-core.json`: the success page's api and token calls.

**The runs:**
- `80`: e3 stage alone, green.
- `81`: complete run, **failed** on T-04-34 with the capture (`81-enviada-add-dog-failure-core.json`, `-375.png`, `81-oauth-token-calls.log`).
- `86`, `87`, `88`: complete runs without the fix, green.
- `92`: complete run with the fix, green.
- `106`, `107`, `108`: the three final complete runs, green.

**What the failure shows:**
- At 04:21:06.070 the success page's `load` fired with the refresh cookie in the jar: `ah_refresh(127.0.0.1/oauth2/token; expires=2026-10-31…; HttpOnly; SameSite=Strict)`.
- No token request followed.
- The page's 136 module requests all answered 200. The last one, at 06.071, was `@vite-plugin-pwa/virtual:pwa-register`: the `await import` in `bootstrap()` right before `refreshBranding`.
- `GET /api/v1/branding` never finished. The body stayed empty, with no console error and no page error. `localStorage` held the cached branding.
- In every passing run, the same load is followed within about 30 ms by `branding 200`, `POST /oauth2/token 200` (cookie sent) and `/me 200`. In `106`: load at 45.967, branding at .978, token at .989, `/me` at .994 (`106-oauth-token-calls.log`, `106-enviada-add-dog-boot-core.json`).

**What it rules out**, over 1,762 token calls in 9 instrumented runs:
- No two renewals ever ran at once (`overlap=no` on every line).
- Every successful refresh set the rotated cookie (`Path=/oauth2/token; Max-Age=2592000`). No `Set-Cookie` was lost.
- The `cookie=none … REFRESH_EXPIRED` lines the E6-W04 review read as the lost session belong to other contexts: anonymous public signup pages (`c2`, `c5`, `c6`, `c7` in `80`), whose boot tries a refresh with no cookie, as expected.
- The only refreshes refused with a cookie sent are one per run in E1's T-01-22 (`apps/id`'s `/login` resuming a flow, a passing test).
- So it is neither INC-36 (a rotated token reused, two renewals racing) nor a cookie path.

**The web's defect:**
- `bootstrap()` (clubs and back office) awaited `refreshBranding`, which had no time limit, before rendering anything.
- One unanswered read left the page blank for good, even with a cached branding at hand.
- **Fix:** with a cached branding, the boot gives the read `BRANDING_BOOT_TIMEOUT_MS` (4 s), aborts it and starts with the cache. Without a cache it waits as before.
- `packages/api-client/src/branding-cache.test.ts`: `89` timed out at 5 s before the fix; `90` is green after it.

**Not proven: which hop held the request** (Vite's dev proxy or the core).
- In `81` the dev servers' output (stdout was piped for that run) shows no proxy error and no dependency re-optimisation.
- The failure probes were added after `81`, and no failure has happened since (6 complete runs).
- None of the final runs `106`–`108` hit the stall either: their boot record shows branding answering in milliseconds. So those three runs prove the suite green, not the fix at work; the unit test proves the fix.
- **25's link** (E6-W04 review #8): a plain click now moves in the app (`navigateInApp`). `82` before, `84` after.
