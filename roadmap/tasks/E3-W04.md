## Steps
1. **Success message tone (review #2).** «Les dades s'han actualitzat.» (`signupReview.saved`) renders as `Toast tone="success"`. Errors keep `danger`. Store the tone together with the message. Vitest: after EDITA LES DADES, the toast has the success tone.
2. **ICU plural (review #4).** `signupReview.pending` becomes an ICU plural in ca/es/en:
   - ca: `{count, plural, =0 {pendent des d'avui} one {pendent des de fa # dia} other {pendent des de fa # dies}}`;
   - es: `{count, plural, =0 {pendiente desde hoy} one {pendiente desde hace # día} other {pendiente desde hace # días}}`;
   - en: `{count, plural, =0 {pending since today} one {pending for # day} other {pending for # days}}`.
   Check the D1 «Preinscripcions pendents» card uses the same form. Vitest for 0, 1 and 5 days.
3. **Null-tolerant D2 (review #3, INC-08).** The core sends `null` for absent optional fields (INC-08, fixed later in the api). D2 must not crash or send `null` back:
   - `paymentMethod`, `upfront`, `plan`, `maskedAccount`, `channel`: use `== null` checks;
   - `familyGroupId`: never send `familyGroupId: null` unless the admin removes the group.
   Vitest with an MSW response where these fields are `null`.
4. **One masked-IBAN format (R-03-27).** The api proposal from round 2 (country + check digits) is **rejected**:
   - S03 R-03-27 fixes one format, and the IBAN never leaves the API beyond the last four digits (GDPR minimisation);
   - the «ES02 ···· 7719» of the D2 mockup is illustrative.
   
   Add `fmtMaskedIban(maskedAccount)` in a shared package. It takes the last four characters of whatever masked string the core sends and returns «···· ···· ···· ···· 1332», or `null` when there is no account.
   - Use it in D2, D5 (`CensusListPage`), D10 (`CensusRecordPage`), screen 19 in add-dog mode (`SignupPage`) and screen 28 (`SelfServicePages`).
   - Remove `compactMaskedAccount`.
   - Vitest: T-03-03 (front half), with both input forms the core sends today («···· 1332» and «···· ···· ···· ···· 1332»), plus `null`.
5. **E2E date proof (review #1).** In `e3-signup.spec.ts`, type a date different from the core's proposal (`01/11/2026`). Assert that `POST /members/{id}/validation` sends `nextInvoiceDate: "2026-11-01"`.
6. **INC-07 evidence (no retries).** Add a small helper to `e2e/core` that records every `POST /oauth2/token` of the run: time, `grant_type`, status, and, for a non-2xx response, the JSON body (`error`, `error_description`, `code`).
   - On a failed test, attach the list to the test output.
   - At the end of each stage, write it to `roadmap/evidence/<subdirectory>/oauth-token-calls.log`.
   - Do **not** add retries or relax the `200` assertions: the point is to catch the next occurrence with its body.
   - If the `400` shows up during this task's runs, quote the log lines in the report. Do not fix the auth flow here.
7. **Re-shoot** `D2-signup-core-1280.png` and `D10-abonat-core-1280.png` with `pnpm e2e:core E3-W04`.
