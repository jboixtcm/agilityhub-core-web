# E9-W01 · The `course-core` JSON Schemas for the core

## Objective
S16's server checks a course only against a JSON Schema (R-16-01). The geometry lives in `course-core`, on the client.

E0-W08 brought `course-core` and `shared-types` into the monorepo, but left the schema export for S16's first task (S16 §14.5, WP-16-A′). This task publishes the two schemas that the api's E9-T01 validates with:
- the course's `CourseData` (the `normalizedJson` the core stores);
- the Unity app's contract, `BuildSessionExportV1` (A9: it stays byte for byte).

Ruling E84 settles the versioning. `CourseData` has no version field, and adding one would change `BuildSessionExportV1`, which embeds it. So the version lives in each schema's file name and `$id`, and the core stores it next to the course.

**Each check comes with a test that fails without it.**

## Spec references
- S16 R-16-01, T-16-03 (amended 01-10, ruling E84), §14.2 (the model aligned with the planner) and §14.5 (WP-16-A′).
- Ruling E77 (one placement engine, on the client; `BuildSessionExportV1` byte for byte) and E84.

## Context to load
- `packages/course-core/src/schema/*.ts` (`courseDataSchema`), the Smarter parser (`parseSmarterTxt`) and `packages/course-core/fixtures/smarter/` (8 files).
- `packages/shared-types/src/build-session-export.ts` (`buildSessionExportV1Schema`, `buildBuildSessionExportV1`) and its tests.
- `packages/api-client`'s Ajv setup (`ajv`, `ajv-formats`, in the catalog).

## Steps
1. **One generator for both schemas.** Put it in `packages/shared-types/scripts/export-json-schemas.ts`, since shared-types already depends on course-core. Run it with `pnpm --filter @agilityhub/shared-types schema:export`.
   - Use `zod-to-json-schema` (a new devDependency, through the catalog), with target draft-07.
   - Write `packages/course-core/schema/course-data.v1.schema.json` from `courseDataSchema`, with `$id` `https://schemas.agilitydoghub.com/course-data/v1.json`.
   - Write `packages/shared-types/schema/build-session-export.v1.schema.json` from `buildSessionExportV1Schema`, with `$id` `https://schemas.agilitydoghub.com/build-session-export/v1.json`.
   - The output must be deterministic: 2-space JSON with a final newline. Use no external `$ref`: inline or local `definitions` only, so a Java validator can load each file on its own.
   - Never change the zod schemas (E84, A9). If a construct does not translate, say so in the report instead of changing it.
2. **A drift check.** A test regenerates both schemas in memory and compares them with the committed files byte for byte. A zod change without a regenerated schema then fails CI, as the api's snapshot test does.
3. **T-16-03 (ruling E84).**
   - Every Smarter fixture → `parseSmarterTxt` → `CourseData` → valid against `course-data.v1.schema.json` (Ajv, draft-07, with formats).
   - Invalid: a `CourseData` without a required field, one with an unknown obstacle type, and one with a negative `designLengthMeters`.
   - A `BuildSessionExportV1` built from fixture rows, as shared-types' tests do → valid against `build-session-export.v1.schema.json`. With `schemaVersion: 2` → invalid.
4. **Documentation.**
   - `course-core`'s README: the two schemas, how they are versioned (a breaking change publishes a `v2` next to the `v1`, and the core stores the version), and how to regenerate them.
   - A CHANGELOG line.
5. **The api's copy.** The web does not write to the api repo. The organizer copies the two files into the api for E9-T01, byte for byte. Give both `sha256` values in the report.

### zod constructs and how they translated (evidence item 3: none failed)

Every construct used by the two schemas translated. There are no effects, refinements, transforms, pipes, lazies or brands: `grep` of `packages/course-core/src/schema`, `src/warnings/types.ts` and `build-session-export.ts` finds none.

| zod | JSON Schema |
|---|---|
| `z.object` | `type: object` + `properties` + `required` |
| `z.string`, `.min(1)` | `type: string`, `minLength` |
| `z.number`, `.int` | `number` / `integer` |
| `.positive()` | `exclusiveMinimum: 0` |
| `.nonnegative()` | `minimum: 0` |
| `.min(0).max(586)` | `minimum` / `maximum` |
| `z.boolean` | `boolean` |
| `z.literal` | `const` |
| `z.enum` | `enum` |
| `.nullable()` | `type: [T, "null"]` or `anyOf […, {type: null}]` |
| `.optional()` | not in `required` |
| `z.array`, `.min(n)`, `.length(6)` | `items`, `minItems`, `minItems` + `maxItems` |
| `z.record(z.string(), z.unknown())` | `type: object, additionalProperties: {}` |
| `z.unknown` | `{}` |

Two meanings that JSON Schema cannot carry are listed in the README and here:

- **A2, zod's `strip` mode.** zod drops unknown keys. The schema rejects them: `additionalProperties: false`, which is zod-to-json-schema's default rendering of `strip`. A test pins it.
- **A3, `.default(x)`.** zod fills in the value. The schema leaves the field out of `required` and carries a `default` annotation, which validators do not apply.

The web always sends zod-parsed values, which carry every default and no unknown key.
