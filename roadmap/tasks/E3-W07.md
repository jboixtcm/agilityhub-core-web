## Steps
0. **Adopt the staged snapshot.** This is the adoption task for the api snapshot that contains E3-T08 and E3-T09:
   - swap `openapi.next.json` in, prune `pending.json`, run `pnpm api:generate`, and fix the type errors;
   - check that it has `planOptions`, `warnDays`, the dog `version`, the readmission blocks, and the per-plan quote of `GET /signup`;
   - if any of them is missing, stop and ask in the report.
1. **M12 · the dog's own version (R-04-19).**
   - The dog `PATCH` sends `signup.version`, which is the member's version (`SignupReviewPage.tsx:150-158`). After an add-dog or a member edit, every dog edit answers 409.
   - Send each dog's own `version`.
   - After a partial save (the member saved, the dog failed), reload.
   
   Vitest.
2. **M13 · 422 codes on their fields (§2 D2).** Today only `details.fieldErrors` is mapped (`:50-59`, `:329-332`), but the api answers bare codes.

   | Code | Shown on |
   |---|---|
   | `LEVEL_REQUIRED`, `LEVEL_NOT_ACTIVE` | the dog's «Nivell inicial» |
   | `NEXT_INVOICE_DATE_REQUIRED`, and a `VALIDATION_ERROR` on `nextInvoiceDate` | the date |
   | `UPFRONT_AMOUNT_EXCEEDS_DUE` | the amount; the input also gets `max` = the amount due |
   | `PLAN_NOT_AVAILABLE` | the plan selector |
   | `INVALID_STATE` with `details.reason = CHECKOUT_PENDING` (E39) | the plan card |
   | `MEMBERSHIP_EXISTS` | a banner |
   | any other code | `errors:{code}` |

   MSW answers like the api: bare codes with empty details. Vitest: one table test over the codes.
3. **M14 · both contacts and the full edit drawer (R-04-19, R-04-03).**
   - Today the drawer rewrites `contactEmails` and `phones` as one-element arrays (`:185-212`), so fixing the first email deletes the second. Edit the element and keep the others.
   - Add the missing fields:
     - gender;
     - the second email and the second phone;
     - the notes to instructors;
     - `holderTaxId`;
     - the requested plan, read-only;
     - the dog documents: add and remove, forwarding the signed upload headers.
   - In add-dog mode (an ACTIVE member), the person block is read-only and only the pending dogs can be edited (R-04-25).
   
   Vitest: editing the first email keeps the second.
4. **M15 · the plan and family decisions (§2 D2, R-04-13, T-04-33).**
   - The plan/price selector lists `planOptions` (api E3-T08) and sends `planId` and `priceId` together.
   - Each change runs `dryRun` and renders the whole response: the upfront lines, the price, `nextInvoiceDate` and the warnings.
   - A family claim that is not FOUND:
     - shows what the applicant typed (the holder's name, the dog's name);
     - offers a member search to attach the holder's group (`familyGroupId`), and an explicit «sense grup» decision.
   - A FOUND claim shows the group, with «tarifa familiar en validar».
   - A FOUND claim whose holder has no group yet validates **without** `familyGroupId`: the api creates the group (R-04-13, T-04-16). Today D2 blocks it with the generic error (`SignupReviewPage.tsx:362-371`; Codex review of E3-W04, finding 1), and `SignupReviewPage.test.tsx:109` asserts that rejection: make it assert a successful POST without the field.
   
   Vitest:
   - a change to Pack 6 → the `dryRun` lines are updated;
   - a `NOT_FOUND_PENDING` claim is resolved both ways.
5. **M11, web side · D1 fresh after a decision (R-14-01).**
   - D2 reads `warnDays` from the signup view, and never calls `/dashboard`.
   - After VALIDA or REBUTJA, navigate to `/tauler` and refetch.
   - A member with nothing pending (`409 INVALID_STATE`, `details.reason = NOT_PENDING`) shows «Aquesta preinscripció ja s'ha resolt», with a link to D10. Add the key in ca, es and en.
   - Remove the `waitForTimeout(1_000)` and the `/abonats` detour from `e3-signup.spec.ts:400-401`. The e2e must be green without them.
6. **Readmission (E38).** D2 shows the badge «Readmissió» and, for each changed field, old → new, from the api's current and submitted blocks. Vitest.
