# E4-W13 · D2 for the reused dog of a readmission

## Objective
Api E3-T17 extended E38 to the dog of a readmission. The reused dog keeps its record until validation, and the submitted values and documents wait in the request. While the readmission is pending, the routes that would write the dog's record answer `409 INVALID_STATE` with `details.reason = READMISSION_PENDING`. D2's edit drawer still uses some of those routes for documents. Api E5-T19 adds each file's `fileKey` to D2's view and a plain id for signup files, so D2 can add or remove one file. This task adopts both. The organizer opens it once api E5-T19 is verified and its snapshot is staged.

**Each fix comes with a test that fails before the fix.**

## Steps
0. **Adopt the staged snapshot:** E3-T17 (`SignupDogView.readmission`, `SignupDogReadmission`, `SignupDogValues`, the documented 409s) and E5-T19 (`files[].fileKey`, the plain file ids). Prune the matching `pending.json` entries.
1. **D2 shows the reused dog's changes (R-04-06).** For a dog with `readmission`, the readmission block lists each field of `changedFields` with «Abans» (`readmission.current`) and «Ara» (the view), as it does for the member. `documents` shows the old and the new document rows. Vitest.
2. **The edit drawer for a reused dog (R-04-19).**
   - Its values and documents change only through `PATCH /dogs/{id}`: replace a type, add one file (the upload plus the kept `fileKey`s), or remove one file (send the kept ones).
   - The drawer never calls the frozen routes for that dog: `POST /dogs/{id}/documents`, `DELETE …/files/{fileId}`, the photo route, and `handlerName`/`licenses`.
   - If a `409 READMISSION_PENDING` still arrives, the drawer shows the new literal:
     - ca «La readmissió està pendent: la fitxa del gos no es pot canviar fins que es validi o es rebutgi.»;
     - es «La readmisión está pendiente: la ficha del perro no se puede cambiar hasta que se valide o se rechace.»;
     - en «The readmission is pending: the dog's record can't change until it is validated or rejected.».
   - After a `PATCH` or a file removal, D2 re-reads `GET /members/{id}/signup`, because the `PATCH` answers the record.
   - A kept file keeps its stored name: the drawer offers no rename. A removed file's key answers `400 FILE_NOT_FOUND` once api E5-T21 is in: the drawer shows the error and re-reads the view.
   - Vitest.
3. **The reused dog's chip is read-only on D2** while the readmission is pending (R-04-06 b), with the same literal as its hint. Vitest.
4. **File removal on the dogs of public signups (api E5-T19 step 2).** The drawer's file removal works on a pending public-signup dog. Real-core e2e.
5. **Mocks behave like the api:**
   - the frozen routes answer 409 for a reused dog;
   - `PATCH /dogs/{id}` with `documents` merges by type;
   - the D2 view carries `readmission` and the `fileKey`s.
   
   Mock tests.
6. **The real core.** Extend the E3 stage of the real-core e2e:
   - a readmission reuses the seed's dog, with a new name and a new card;
   - D2 shows «Abans / Ara» for the dog;
   - a rejection leaves the dog as it was on D10.
