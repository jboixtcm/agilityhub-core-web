## Fixed conventions
- Design system only; keys never literals; ca/es/en together; vocabulary rules (never «parell*», «amigable», «(paràmetre)» or requirement codes; the red state is «no presentat»).
- The api decides: badges, `counts`, `detail.kind`, metrics, `version` and signed urls are rendered as delivered; the front never derives a cancellation reason, a percentage or a month window, and never stores an attachment url (they expire in 5 minutes — refetch instead).
- Errors are handled by `code` through `errors:<CODE>`, never by HTTP status (E6-T01 re-mapped `TASK_ALREADY_DONE`, `TASK_NOT_DONE`, `DOG_NOT_ACTIVE`, `ATTACHMENT_LIMIT_REACHED`, `ATTACHMENT_ENTITY_MISMATCH` to **422** under `CATALEG_ERRORS.md` rule 0) and never by showing the api `message` as copy.
- Uploads always go through the signed-url flow of `CONVENCIONS_API.md` §5 with the purposes `TASK` and `DOG_OBSERVATIONS`; the file is validated against `files.maxSizeMb`, `files.allowedTypes` and `files.maxAttachmentsPerEntity` read from the club parameters, never hard-coded.
- Closed catalogs: no new parameter, event, notification or error code. Proposed literals («Encara no hi ha res a l'històric», «Vols eliminar aquesta tasca?», the «Vas avisar el club…», «Pel club en nom teu…» and «Per inactivitat o baixa…» detail lines) go to the report and `roadmap/MESSAGES.md` while shipping with the wording above (S10 §13-11).
