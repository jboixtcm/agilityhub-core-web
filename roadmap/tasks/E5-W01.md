# E5-W01 · Screens 03, 04, 06/29 and 07 — class bookings and waitlist (S08 front)

## Objective
Work packages S08 WP-08-E and WP-08-F: a member sees her reservations on 03, picks a class on 04 with **one** dog selected and remembered, confirms it on 06/29 while the seat is held for 30 s (swapping an existing booking when the week limit is reached, paying first when the club sells single classes), opens 07 to cancel it with the 4 h threshold wording, and joins, consults or leaves a waitlist. Everything is decided by the api: the front renders `state`, `limit`, `displayState`, `opensAt`, `price` and never recomputes a week, a limit or a threshold. Mocks-first on the S08 schemas of api E5-T01; pixel-faithful to the V8 mockups at 375 px.

## Fixed conventions
- The api decides: row `state`, `limit`, `swappable`/`notSelectable`, `opensAt`/`nextBookableAt`, `displayState`, `price`, `instructorVisibleAt`, `calendarLinks`. The front never computes a booking week, a limit, a threshold or a row state, and never re-orders `reservations[]`.
- Closed catalogs: no new error code, parameter, event or notification. Map errors **by `code`**, never by HTTP status and never by the api `message`; the statuses in force are `CLASS_FULL`, `SEAT_TAKEN`, `SEAT_HOLD_EXPIRED`, `BOOKING_LIMIT_REACHED`, `WAITLIST_LIMIT`, `ALREADY_BOOKED`, `ALREADY_ON_WAITLIST`, `IDEMPOTENCY_KEY_REUSED` **409**; `NOT_YET_OPEN`, `CLASS_NOT_BOOKABLE`, `LEVEL_NOT_ALLOWED`, `PACK_EMPTY`, `MEMBER_NOT_ACTIVE`, `BOOKING_BLOCKED`, `INACTIVITY_PERIOD`, `CLASS_NOT_FULL`, `WAITLIST_FULL`, `WAITLIST_NOT_NOTIFIED`, `WAITLIST_OFFER_EXPIRED`, `WAITLIST_ENTRY_NOT_LIVE`, `SWAP_NOT_ALLOWED`, `BOOKING_NOT_CANCELLABLE`, `WEEKLY_LIMIT_DONE` **422**; `MODULE_DISABLED`, `NOT_FOUND`, `DOG_NOT_ACCESSIBLE` **404**.
