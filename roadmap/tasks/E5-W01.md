# E5-W01 · Screens 03, 04, 06/29 and 07 — class bookings and waitlist (S08 front)

## Objective
Work packages S08 WP-08-E and WP-08-F: a member sees her reservations on 03, picks a class on 04 with **one** dog selected and remembered, confirms it on 06/29 while the seat is held for 30 s (swapping an existing booking when the week limit is reached, paying first when the club sells single classes), opens 07 to cancel it with the 4 h threshold wording, and joins, consults or leaves a waitlist. Everything is decided by the api: the front renders `state`, `limit`, `displayState`, `opensAt`, `price` and never recomputes a week, a limit or a threshold. Mocks-first on the S08 schemas of api E5-T01; pixel-faithful to the V8 mockups at 375 px.

## Fixed conventions

### Assumptions
1. **Activities on 03.** ACTIVITY rows of `/me/home` are drawn with E4-W04's `ActivityReservationRow`. The mock sends them only in the «Tots» view, because an activity registration is linked to the member, not to a dog (04 V3).
2. **Mapping ACTIVITY rows.** `ReservationRow` carries no `activityId`, so each row is matched to `/me/activities` `mine[]` by its registration id (question 2).
3. **TRAINING rows** render with «confirmada» and no link. Screen 08 / `/entrenaments/{id}` belongs to E5-W02, so the row stays inert until it lands (the «inert» case of step 2).
4. **«Reservada per» (07).** `BookedBy` has no id or «self» flag, so 07 compares `bookedBy.displayName` with the first name of the session account. When they are equal it reads «Reservada el …» (question 3).
5. **Two names in the member scenario.** The mock keeps the mockup's «Hola, Laura!» in `/me/home`, for the pixel comparison. The session account of the shared `member` scenario is the E2 fixture «Biel Roca», so the mock's `bookedBy` follows the session name. Both names are fictional.
6. **Idempotency-Key.** There is one key per distinct payload: hold + swap choice, or claim. A retry after a network error or a 5xx stays on the page and resends the same key, so the api deduplicates it (T-08-16). Choosing another swap makes a new payload and a new key. I read the task's «a fresh Idempotency-Key per attempt» this way; R-08-08 says «`Idempotency-Key` (= `seatHoldId`)» (question 4).
7. **Hold release.** `DELETE /seat-holds/{id}` runs on «CANCEL·LAR LA NOVA RESERVA», on the back gesture and on unmount. The unmount release waits one tick so that React StrictMode's remount does not release a live hold.
8. **Where the hold lives.** It travels in `history.state` (the router state). A reload with no state goes back to `/reservar`.
9. **Browser mock.** The MSW booking world is persisted in `sessionStorage` (`agilityhub.mockBookings`) so that full page loads in Playwright keep the bookings. `resetBookingMockState()` clears it.
10. **Initial dog on 04.** It is the api's `dog` (R-08-23 `lastDogForClass`, server-side). Nothing is persisted in the front.
