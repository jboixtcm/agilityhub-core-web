## Steps
1. **A retry answered `IN_PROGRESS` keeps its key (review #1, major; R-11-13, CONVENCIONS_API §7).**
   - Today `409 IDEMPOTENCY_KEY_REUSED {reason: IN_PROGRESS}` drops the submission's key. The next retry then creates a second announcement while the first one can still complete.
   - `IN_PROGRESS` is not the submission's answer: keep the key, say that the send is still in progress, and retry with the same key. Only a final answer retires the key (E74).
   - Test the whole sequence: a network failure → a retry with the same key → `IN_PROGRESS` → another retry with the same key → one batch.
2. **The count and the confirmation belong to the latest dry run (review #2, major; R-11-13).**
   - Today the count shown is matched by template and recipients, not by request. A → B → A before B answers brings A's old count back, and its tick enables ENVIA.
   - Clear the count as soon as the template or the selection changes. The count, the tick and ENVIA belong to the latest dry-run request only: until it answers, nothing can be sent.
   - Test with delayed answers: A answers 11, switch to B, back to A before B answers → no count, ENVIA disabled, no send call; A's new answer arrives → its count shows and the tick is empty.
3. **D10's preference writes keep their order when the admin leaves (review #3, major; R-11-04).**
   - Today leaving sends a combined PUT alongside a PUT still in flight. If the keepalive PUT lands first, the older PUT saves its older value last and the outbox is cleared.
   - The latest choice must win, whatever order the answers arrive in: send the writes one after another (the keepalive PUT carries the latest state), or make an older answer unable to overwrite a newer write. Keep the recovery entry until the latest change is confirmed.
   - Test: PERSONAL = false in flight, the admin sets it back to true and leaves, and the answers arrive in reverse order → true is saved and nothing is lost.
4. **Saving still works after a back-forward cache restore (review #4, major; R-11-04).**
   - Today a flag set on `pagehide` stays set after `pageshow` with `persisted`. Later departures then skip both the keepalive save and the outbox.
   - On `pageshow` with `persisted`, restore the saving lifecycle and reconcile the writes still pending.
   - Test: `pagehide(persisted)` → `pageshow(persisted)` → a change → leave at once → the PUT is sent and the outbox holds it.
5. **An older save answer never replaces a newer one (review #5, minor; R-11-12).**
   - Today the late-save guard checks the template's id but not the answer's freshness: save A, reopen A while the answer is delayed, save again → the older answer brings version 4 back over version 5.
   - Ignore an answer older than the one already applied, by `version` or by request order, for saves and for overlapping detail reads.
   - Test: two completed saves of the same template whose answers arrive in reverse order → version 5 stays, with no draft lost.
